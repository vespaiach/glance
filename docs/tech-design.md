This document records the technical decisions. **What** the app does is in the product spec (requirement IDs like `SYNC-02` refer to it). This document covers **how** it's built. If they conflict, the spec wins on behavior and this document wins on implementation.

## 1. Decisions at a glance

| # | Area | Decision | Why |
|---|---|---|---|
| D1 | Framework | **Next.js (App Router), run as a SPA.** A persistent client shell lives in `(app)/layout.tsx`. Views are `'use client'` segments | Deep links work, and the shell's timers (clock, idle, slideshow, sync) survive view changes (spec §3) |
| D2 | Language / lint | **TypeScript `strict`**, **Biome** (lint + format, in CI and pre-commit) | Spec §3 |
| D3 | Styling | **StyleX** (Babel + PostCSS plugin). Tokens via `defineVars`, seasons via `createTheme`. Setup (F02): ESM `babel.config.js` (`next/babel` + `@stylexjs/babel-plugin`, `runtimeInjection: false`, `@/*` alias for `.stylex.ts` imports) and `postcss.config.js` reusing its plugins over `app/` and `src/` with `useCSSLayers: true`. `app/globals.css` holds only `@stylex;` (Biome allows that one at-rule). Turbopack picks up the Babel config in dev and build | Spec §3, §4. No CSS modules, no Tailwind, no inline `style`. CSS layers keep StyleX priorities without the `:not(#\#)` specificity hack. Tokens (F03): `tokens.stylex.ts` holds `colors`, `space`, `radii`, `shadows`, `motion` and `sizes` (touch, icon button, kiosk canvas, fluid gutter); `type.stylex.ts` holds `type` with the §4.3 fluid values; `seasons.stylex.ts` holds `season` (Spring values); `themes.ts` holds the `summer`/`fall`/`winter` themes and `ambientType`. The handoff's `--surface-hero/weather/notes/highlight/warm/deep` aliases are not ported: a var declared on `:root` would not follow a theme set lower down, so components use the `season.*` roles directly (spec §4.1 role table). `--season-name` comes from `copy.ts`. Fonts and icons (F04): Geist and Geist Mono variable woff2 files (from the `geist` npm package, OFL) are vendored in `src/theme/fonts/` and loaded by `src/theme/fonts.ts` with `next/font/local` (`weight: "100 900"`), so they are served from `/_next/static/media` and precached with the build. The root layout puts their `--font-geist-sans` / `--font-geist-mono` classes on `<html>`, and `type.fontSans` / `type.fontMono` start with those vars instead of the handoff's `'Geist'` / `'Geist Mono'` names (next/font hashes the family name). `<body>` gets `type.fontSans` and the body weight. `src/ui/Icon.tsx` wraps `lucide-react` (pinned 0.460.0): it takes the glyph component (`icon={House}`), not a name string, so unused icons tree-shake; size 24, stroke 1.75 below 48 px and 1.5 from 48 px, overridable (1.25 for large weather glyphs), round caps and joins, `currentColor`, `aria-hidden` |
| D4 | Client data | **Custom local-first store on IndexedDB (Dexie).** The UI reads local data only, writes go local first, and a sync engine in a Web Worker (D19) handles the server | Offline is a core requirement (OFF-*). One code path for online and offline. Small bundle, no RxJS, and the sync rules (D9, D10) are ours to read and change. **Rejected:** RxDB, which has its own replication but adds RxJS, a bigger bundle and a second JSON schema per collection. Dexie Cloud, which replaces our backend with its own server, PostgreSQL and auth. Dexie.Syncable, a legacy addon |
| D5 | Shell state | **React context + `useSyncExternalStore` stores.** No state library | Little shell state. External stores keep the 1 s clock tick from re-rendering the whole tree |
| D6 | Validation | **Valibot** schemas in `src/domain` are the single contract. Types come from `v.InferOutput`. Schemas (F05, `valibot` pinned 1.5.0): `src/domain/schemas.ts` holds one `XSchema` per spec §7 type (`CalendarEvent`, `Note`, `Photo`, `AccountSettings`, `Weather`, `Account`, `Display`, plus `Tone`, `NoteTone`, `Season`, `WeatherIcon`, `WeatherLocation`) and a `SyncedXSchema` for each synced entity (events, notes, photos, settings) that adds `updatedAt`, `version` and an optional `deletedAt`; `Synced<T>` is `T` plus the inferred server fields. IDs are UUID strings, timestamps ISO-8601 (`v.isoTimestamp`), `takenOn` and daily `date` ISO dates. Required text (title, note text, author) must not be blank; schemas never transform, so parsed output equals the stored row. The event schema also checks `endAt > startAt` and a span under 24 h (§6.1), so the server gets that rule from the contract. `Weather` icons are a closed set of Lucide kebab names (`sun`, `cloud-sun`, `cloud-rain` …) that `ui` maps to components, because `domain` can't import Lucide. Hourly has exactly 8 points and daily 7. Photos have no `updated_at`/`deleted_at` column in spec §7.0; they are immutable and never deleted in v1, so the server fills `updatedAt` from `created_at` (B lane). Handoff v5 changes this (D22, planned): photos get those columns and sync like events. `src/domain/defaults.ts` holds `DEFAULT_SETTINGS` (spec §7.0 defaults). The "blank author → Guest" rule (NOTE-03) is applied by the note form with `copy.notes.guestAuthor`, not by the schema | Shared by client and server. Small bundle |
| D7 | Database | **PostgreSQL** via `pg` (a Pool), **raw SQL** with `$n` parameters behind a small `Db` interface; tests run on **PGlite** (`@electric-sql/pglite`, Postgres in WebAssembly, no server needed). Setup (P01, `pg` 8.23.1 with `@types/pg` 8.23.1, `@electric-sql/pglite` 0.5.8 as a dev dependency): `server/db/db.ts` `Db` = `all(sql, params)` → rows, `one` → first row or `undefined`, `run` → changed row count, `exec(sql)` for multi-statement SQL (migrations), `tx(fn)` → `BEGIN`/`COMMIT`, `ROLLBACK` when `fn` throws (a `tx` inside `tx` joins the outer one). `pgDb(pool)` / `openPgDb(url)` is the `pg` adapter; `server/db/pglite.ts` `pgliteDb(client)` / `openPglite()` (with the `citext` extension) is the test adapter, kept out of `db.ts` so the runtime never imports a dev dependency. Both share `PG_PARSERS`: `timestamptz` → ISO string (`toISOString()`, whatever the session time zone), `bigint` → number, `date` stays `YYYY-MM-DD`; `jsonb` comes back parsed. Migrations: `db/migrations/NNN_*.sql`; `server/db/migrate.ts` `readMigrations(dir)` reads the three-digit files in order and `migrate(db, migrations)` creates `schema_migrations(version, applied_at)` if needed and applies each file not recorded there in its own transaction that also records its version, so a failed file leaves the last good version. `001_init.sql` is the spec §7.0 schema (L08's `002_setup_done` folded in, since the data starts fresh) plus the single `sync_state` row at version 0. Migrations are read from `process.cwd()/db/migrations`. Server tests get a fresh migrated PGlite DB per test (`migratedDbPerTest`, a clone of one migrated DB per file). **Runtime (P02):** `getDb()` (`db.ts`) is one `pg` Pool on `globalThis` from `env().DATABASE_URL`; `bootServer()` awaits `migrate(getDb(), …)` and exits on failure. Every service, auth and job function takes the `Db` and is `async`; route handlers and the job tick `await` them. `better-sqlite3` and the SQLite migrations are gone | Spec §3, open item D resolved; moved from SQLite to PostgreSQL in Phase 8 (spec v0.40) |
| D8 | IDs | **UUIDv7, generated on the client** (`uuidv7(now, random?)` in `src/domain/id.ts`, no dependency; random bytes default to `crypto.getRandomValues`, I01) | Offline creates need no ID remapping. They sort by creation time |
| D9 | Sync | **Outbox push + versioned pull.** SSE only says "something changed"; polling every 30 s is the fallback | See §5. Refines SYNC-02 |
| D10 | Conflicts | **Last write to reach the server wins.** The server stamps `updated_at` and `version` | Display clocks can drift. Server order is the one order everyone agrees on (refines SYNC-03) |
| D11 | Auth | Magic link, opaque session token in an **httpOnly cookie**, stored hashed. The waiting screen **polls every 2 s**. Tokens and pending ids are 32 random bytes (base64url); only the sha256 of a link or session token is stored. Account and display ids are server-made UUIDv7. Cookies (B02): `session` (400 days, the browser cap, so a kiosk restart keeps it), `pending` (1 day) and `link_email` (10 min), all `HttpOnly; SameSite=Lax; Path=/`, `Secure` when `APP_URL` is https. See §6.2 | Spec §8.1. Polling is enough for a 10-minute window |
| D12 | Photos | Files on disk under `{DATA_DIR}/photos`. **`sharp`** makes a display (≤ 2560 px) and a thumb (≤ 640 px) WebP copy on upload. As built (B05): `sharp` pinned 0.35.5 and `exif-reader` pinned 2.0.3. Files are `{DATA_DIR}/photos/{account}/{id}.{orig|display|thumb}`; `photos.file_path` holds `{account}/{id}`. The copies are turned upright by EXIF orientation; the original is kept byte for byte. Accepted formats are the raster ones `sharp` decodes (JPEG, PNG, WebP, GIF, AVIF, HEIF, TIFF); SVG is refused, since a served SVG could run script | 20 MB originals are too heavy for a kiosk grid |
| D13 | Weather | **Open-Meteo** (forecast + geocoding) behind a `WeatherProvider` adapter. Settings store the chosen place with its coordinates. Server cache per account, 15 min TTL. As built (B06): `server/weather/provider.ts` holds the `WeatherProvider` interface (`forecast(coords, now)` → a `Weather` without `location`, `places(query)`, both `Result<…, "weather-failed">`); `openMeteo.ts` `createOpenMeteo(fetch)` asks `api.open-meteo.com/v1/forecast` (°F, mph, Unix time, `timezone=auto`, 7 days) and `geocoding-api.open-meteo.com/v1/search` (`countryCode=US`, English, 20 results) with an 8 s timeout, and parses both answers with Valibot; any network error, non-2xx or wrong shape is `weather-failed`. `forecast.ts` `toForecast` maps the answer: values rounded, WMO code → icon + `WmoCondition` key (`domain/wmo.ts`, night icons from `is_day`), wind direction as an 8-point compass, today's high/low/sunset from the first day, the 8 whole hours after `now`, 7 days dated by the place's local date, and a daily rain chance only from 10%; the result is checked against `WeatherSchema`, so an unknown code or a short series fails. `places.ts`: `placeQuery` splits "City, ST" and searches the city part; `toPlaces` keeps results named like the query (case, accents and punctuation ignored; a 5-digit ZIP keeps every result), in the given state (name or USPS code), with a valid IANA `timezone` (L03: it becomes the place's `timeZone`; a result without one, or with one `Intl` rejects, is left out, LOC-05), one per name + state, at most 5; `placeLabel` names a place "Portland, OR" (`copy.weather.place` with the USPS code, or the region when it has none). `services/weather.ts`: `accountWeather` reads the place from the account's settings row (`no-location` without one), serves `weather_cache` while it is the same `lat,lon` and under 15 min old, else asks the provider and saves the answer; a failure keeps no cache row and answers `weather-failed`. `searchPlaces` passes the query to the provider. **Built (L05, spec LOC-03/04):** `getJson.ts` holds the shared JSON fetch (`Fetch`, 8 s timeout, Valibot parse; any failure is `weather-failed`) used by both adapters. `provider.ts` adds `WeatherProvider.timeZoneAt(coords)` → `Result<string, "weather-failed">` and a `PlaceLocator` port, `placeAt(coords)` → `Result<{ name, region }, "not-found" | "weather-failed">`. `openMeteo.ts` `timeZoneAt` asks the forecast endpoint with only `latitude`, `longitude`, `timezone=auto` and `forecast_days=1` and reads `timezone`; one `isTimeZone` rejects is `weather-failed`. `census.ts` `createCensusGeocoder(fetch)` asks the US Census Geocoder `geographies/coordinates` (`x`=lon, `y`=lat, `benchmark=Public_AR_Current`, `vintage=Current_Current`, `format=json`). Its answer leaves out a geography layer with nothing in it (a point outside the US answers `geographies: {}`), so every layer is optional. The place is named by the `BASENAME` of the first Incorporated Place → Census Designated Place → County Subdivision with a letter in it (Maryland's districts are named "4"), else the first County's `NAME` ("Teton County"); the region is `States[0].BASENAME` ("Oregon", so `placeLabel` gives "Portland, OR" as for search). No state, or nothing to name, is `not-found`. Recorded live answers `census.portland.json` (Portland, OR) and `census.outside.json` (Toronto) are the parse fixtures. `services/weather.ts` `locatePlace({ provider, locator }, coords)` rounds both coordinates to 2 decimals, asks `placeAt` and `timeZoneAt` in parallel at the rounded point, and answers `WeatherLocation` with the rounded `lat`/`lon` and `timeZone`, else `not-found` (checked first) or `weather-failed`; it reads no account data. `services/index.ts` `locatePlace(coords)` wires `createOpenMeteo(fetch)` and `createCensusGeocoder(fetch)`. | Open item B. Free, no API key. Census: public domain, no key, US only like WX-09. **Rejected** for reverse lookup: BigDataCloud's free client endpoint (its terms allow calls from the browser only) and Nominatim (attribution, an identifying User-Agent and 1 request/s, and no time zone) |
| D14 | Email | **[Resend](https://resend.com) HTTP API**, configured by env vars (`RESEND_API_KEY`, `MAIL_FROM`). Plain `fetch` to `POST https://api.resend.com/emails` with a Bearer key and `{ from, to, subject, text }`, no SDK or SMTP library (nodemailer removed in v1.74). `server/mail/mailer.ts`: `createMailer(apiKey, from, fetcher = fetch)` → `{ send }` answering `Result<void, "mail-failed">` (logs and never throws; a non-2xx answer or a network error is `mail-failed`); `signInMessage(to, url)` builds the SIGNIN-12 email from `copy.signIn.email` | Open item E |
| D15 | Time | No date library. **`Intl.DateTimeFormat`** plus pure helpers in `src/domain/time.ts`. Account stores an IANA `time_zone`. TIME-01 formatters take **minutes of the local day** (`minutesOfDay(date)`), so the TimePicker draft and stored events share them: `formatClock` ("10:41 AM"), `timeParts` (time + mono AM/PM), `formatRange` (rows), `formatHour` (hourly), `formatLength` (TPK-01), `formatLongDate` (Clock date, MonthGrid day labels), `formatDayTitle` ("Friday, Oct 9", the Calendar day heading, V02). `month.ts` holds `monthCells` (Sunday-first grid with blank padding), `formatMonthYear`, `weekdayInitials`, and (V02) `monthTitle(year, month, now)` (the month name, plus the year outside `now`'s year, CAL-03) and `markedDays(events)` (the sorted local days that have an event, CAL-02). Weekday and month-day names use `Intl.DateTimeFormat("en-US")`. Days compare by `dayNumber(instant, tz)` (days since 1970-01-01 of the date in `tz`), which is DST-safe. **Zone primitives (L01, built; spec LOC-06):** "local" becomes the screen's time zone `tz`, not the device's (wired through in L02, L04). The pure `domain/zone.ts` holds `wallTime(instant, tz)` → `WallTime` `{year, month (1–12), day, hour (0–23), minute, weekday (0 = Sunday)}` (`Intl.DateTimeFormat("en-US", { timeZone, hourCycle: "h23" }).formatToParts`, one cached formatter per zone), `zonedInstant(tz, {year, month, day}, minutes)` (wall time → instant: with `offset(t)` = the zone's wall time at `t` read as UTC minus `t`, try `wall − offset(wall − 1 day)` and `wall − offset(wall + 1 day)`, keep the earlier one that reads back as the asked wall time, else the first; so a skipped time moves forward by the gap and a repeated one is the earlier instant, east and west of UTC alike; `minutes` past 1440 roll into the next day), `dayNumber(instant, tz)` (replaces `localDayNumber`), `dateKey(instant, tz)` / `parseDateKey(key)` / `addDays(key, n)` (replace `localDateKey` / `parseLocalDate`; `parseDateKey` gives the date's UTC midnight, since a date with no time, such as a month cell, `takenOn` or a forecast day, is a UTC-midnight `Date` formatted in UTC), `dayStart(key, tz)` and `displayTimeZone(settings, fallback)` = `weatherLocation?.timeZone ?? fallback` (typed structurally until L03 adds `WeatherLocation.timeZone`). **Wired through (L02, built):** every helper that reads hours or dates takes `tz` last: `minutesOfDay(date, tz)`, `atMinute(dayKey, minutes, tz)` (`zonedInstant` on the key's date), the `format*` date names (`formatWeekday`, `formatMonthDay`, `formatLongDate`, `formatMonth`, `formatDayTitle`, one cached formatter per options and zone), `month.ts` (`monthTitle`, `markedDays`, `stepMonth`), `seasonFor`, `background.ts` (`rotationStep`, `shownBackground`, `changeBackground`), `notes.ts` (`noteStamp`), `eventStatus`, `todayHero`, `pictureOfDay`, `idle.ts` (`inAmbient`, H02), `eventTimes.ts` (`nextHalfHour`, `defaultTimes`), `ambient.ts` (`isTomorrow`), `nextNotableDay`; `clockAt(iso, clock, tz)` replaces the repeated `formatClock(minutesOfDay(new Date(iso)), clock)`. A date with no time (a day key, `takenOn`, a forecast day, a month cell) is a UTC-midnight `Date` formatted with `"UTC"`, so `monthCells`, `formatMonthYear`, `weekdayInitials`, `readDateParam` and the `MonthGrid` day labels take no zone. `localDateKey`, `parseLocalDate` and `localDayNumber` are gone. `zone.ts` also exports `calendarDate(key)` and `deviceTimeZone()` (`Intl.DateTimeFormat().resolvedOptions().timeZone`), which `useTimeZone()` falls back to when no place with a zone is set (L04). The fixture data and transport use `FIXTURE_TIME_ZONE` (`America/Los_Angeles`, the fixture place's zone) and the gallery samples `GALLERY_TZ` (the same zone), so both read the same in any device zone (L04). `src/localZoneGuard.test.ts` fails if `src` (outside `zone.ts` and tests) calls `getHours`, `getMinutes`, `getDate`, `getDay`, `getMonth`, `getFullYear` or `new Date(y, m, …)` (the UTC getters stay allowed), and `vitest.config.ts` sets `process.env.TZ` to a zone no fixture uses (`Asia/Kolkata`; ICU names it `Asia/Calcutta`, so the pin test compares wall times, not names), so a test passing `America/Los_Angeles` proves the device zone is ignored. `accounts.time_zone` stays as the server's fallback (§6.4) | Few, well-specified formats (TIME-01). Open item C. **Rejected** for LOC-06: a "shifted" `Date` whose device-local fields show the location's wall time. It is a fake instant typed as a real one, so it would leak into `toISOString()` writes, Dexie `between` ranges and `Date.parse` comparisons, and it breaks on wall times the device zone skips |
| D16 | Offline shell | **Serwist** (Workbox-compatible) PWA. Precache build assets, fonts and public files; cache the HTML of every static app route when a SW activates, and RSC payloads as the app fetches them (C04). **NetworkFirst** (3 s timeout) for navigations and RSC requests, falling back to the cache, then `/today`. **CacheFirst** for photo files, with cache warming. **NetworkOnly** for every other `/api/*` call (Dexie owns data). Web app manifest + `navigator.storage.persist()`. New versions activate only when the screen is idle. See §4.5 | OFF-*. Kiosk screens reload rarely, and when they do they must start offline |

| D20 | Location | **Built (server L05, page L06), spec LOC-01..04.** The screen asks the browser for its position (`navigator.geolocation.getCurrentPosition`, low accuracy, 10 s timeout, `maximumAge` 10 min) through an injectable `data/repos/position.ts` `currentPosition()` → `Result<{lat, lon}, "denied" \| "no-position">` (code 1 → `denied`, 2 and 3 → `no-position`), offered only when `"geolocation" in navigator`, `isSecureContext` and the permission isn't already `denied` (`navigator.permissions.query({ name: "geolocation" })` where it exists; a `denied` answer at runtime hides the action too, LOC-03). The browser's permission prompt isn't timed; the 10 s `timeout` covers the position once allowed, and the page aborts the place lookup after 5 s (`lookup`, LOC-02). The failure reasons are `denied`, `no-position` (codes 2 and 3), `outside` (the server's 404) and `lookup` (the 5 s limit, a 5xx, or a `network` answer when the server can't be reached, LOC-03). The server turns the position into a place with its time zone (D13 `locatePlace`). The browser never calls a geocoder itself. **As built (L06):** `position.ts` exports `devicePosition: DevicePosition` = `{ available: canLocate, current: currentPosition }`; `canLocate` reads `globalThis.isSecureContext` (jsdom has none). `useWeatherSetup` races only `locate(coords)` against the 5 s limit, so the permission prompt and the 10 s position wait never count toward it; any locate error other than `outside` is `lookup` | One code path for search and position: both end in a `WeatherLocation` saved like WX-09. Server-side lookup keeps third-party calls behind our adapter and the 2-decimal rounding in one place |
| D21 | All-day events | **Built (U05, handoff v5, spec EVT-08).** An all-day event is `allDay: true` with `startAt` = its date's **UTC midnight** (`parseDateKey(key).toISOString()`) and no `endAt`: a date with no time, like `takenOn` and the month cells (D15). `CalendarEventSchema` checks that `allDay` has no `endAt` and a UTC-midnight `startAt`. Repos read a day as two ranges on the one `startAt` index: timed events in `[dayStart(key, tz), dayStart(addDays(key, 1), tz))` and all-day events at exactly that UTC midnight, each filtered by `allDay`, since a timed event can sit at a UTC midnight too. `eventStatus` gives an all-day event the status `allDay` (never past, now or upcoming) and `todayHero` leaves them out (`nextHalfHour` reads no events, so it needs no change); `markedDays`, the counts and Ambient's "Next event" (`useNextEventAfter`) include them; the LOC-09 example (`useUpcomingEvent`) skips them. `domain/allDay.ts` `eventDayKey(event, tz)` is the one place that reads an event's date: the UTC date for an all-day event, the date in `tz` otherwise. Server: `events.all_day` with `CHECK (NOT all_day OR end_at IS NULL)`; the span checks apply only to timed events | The date must not move when the location's time zone changes (LOC-06) or across DST. **Rejected:** midnight to midnight in the location's zone, which moves to another day when the zone changes and is 23 or 25 hours long on DST days (it fails the < 24 h span rule) |
| D22 | Photo details | **Planned (handoff v5, spec PHOTO-10..13).** **Read on upload, on the server** (B05's path): `exif-reader` gives the title (`ImageDescription`, else `XPTitle`), the date (`DateTimeOriginal`, else `DateTimeDigitized`) and GPS; GPS goes through D13's `PlaceLocator.placeAt` at 2 decimals and `placeLabel` ("Cannon Beach, OR"), and any lookup failure or a place outside the US leaves the place empty, so an upload never fails on it. The file-name rules are pure (`domain/photoName.ts`: `nameFromFile`, `dateFromFile`), so the upload tile can show the same guess while it uploads. The client sends `file.lastModified` as a date in the screen's zone (`x-file-modified`, an ISO date) for the last date fallback; without it the server uses the upload day (`accountTimeZone`, §6.4). The row stores `sources` and `checked` (spec §7). **Editable and deletable:** photos become `Synced<Photo>` with `updated_at`/`deleted_at`; `PUT /api/photos/{id}` updates only `title`, `takenOn`, `place`, `sources` and `checked` (the file never changes), `DELETE` makes a tombstone like events (delete wins) and removes the three files after the transaction commits. Outbox entity `photos` already exists in `OutboxEntry`. The photo file route answers 404 for a tombstone, and the page tells the service worker to drop the deleted photo's cached files with the existing `photosChanged` path | The server already reads EXIF and owns the geocoder (D13), so the browser never parses EXIF or calls a geocoder. Sources are facts about the upload that can't be derived later, so storing them doesn't break the "never store derived values" rule |
| D23 | Screens and QR sign-in | **Planned (handoff v5, spec SET-12, SIGNIN-15).** `GET /api/displays` lists the session's account's displays (type, name, `last_seen_at`, `current`), newest first; it is a read through the transport (`Transport.displays`), not synced into Dexie, since nothing works offline with it. **Rules**
- Screens **never call `fetch`** for app data. They read Dexie through hooks and write through repos. Every server call (sync, weather, place search, auth, upload) goes through the **transport** (`data/sync/transport.ts`), so phases 1–4 run with no backend.
- The sync worker **never posts data to the page**. Data and sync status reach the UI through Dexie. Only `photosChanged` and `restart` are messages.
- The server is the source of truth. The client's IndexedDB is a replica plus a queue of pending writes.
- Weather is **read-through**, not synced: the sync worker calls `GET /api/weather` every 15 min and writes the result to Dexie for offline use.
- Auth screens (sign-in, waiting, name) call the transport directly, not Dexie. They have no offline mode beyond SIGNIN-10.
- Boot decides "signed in" from `glance-meta`, never from the network. The service worker caches the app and photo files, never API JSON. Dexie is the only data cache.

## 4. Client design

### 4.1 Local store (Dexie)
```ts
db.version(1).stores({
  events:   'id, startAt, deletedAt',
  notes:    'id, createdAt, deletedAt',
  photos:   'id, createdAt',
  settings: 'accountId',
  weather:  'accountId',
  outbox:   '++seq, entity, entityId',    // { seq, entity, entityId, op: 'put'|'delete', payload, attempts }
  meta:     'key',                        // cursor, lastSyncedAt, accountId
});
```
- **One database per account** (`glance-{accountId}`). Sign-out deletes it. Fixture/demo mode uses `glance-fixture`, reseeded on each load.
- Rows keep the server's soft delete (`deletedAt`). Hooks filter deleted rows out.
- `syncState: 'pending'` (e.g. "Waiting to post") is **derived**: the row has an outbox entry. It isn't stored.
- **Wire format = domain types** (camelCase, Valibot). Dexie stores them as-is. Snake_case exists only in SQL, and `server/db/queries` maps between the two.
- **Code (S02, `dexie` pinned 4.4.6):** `data/db.ts` exports `openGlanceDb(name)` (applies the schema above, opens lazily), `deleteGlanceDb(name)`, `accountDbName(accountId)` (`glance-{accountId}`) and `FIXTURE_DB_NAME` (`glance-fixture`), plus `CURSOR_KEY` (`cursor`), the `meta` key whose presence means "ever synced" (§4.4). The DB is typed as `Dexie & { table: EntityTable<…> }`, not a `Dexie` subclass. Row types: `StoredEvent` / `StoredNote` / `StoredPhoto` are `Synced<T>`; the single `settings` row is `Synced<AccountSettings> & { accountId }` and the `weather` row is `Weather & { accountId }`, because those tables are keyed by `accountId`. `OutboxEntry` is `{ seq, entity: 'events'|'notes'|'photos'|'settings', entityId, op, payload?, attempts }` (no payload on a delete); `meta` rows are `{ key, value }`, and S04 types the keys it writes. Dexie's default `versionchange` handling closes an open connection, so another context's upgrade is never blocked (§4.6).

### 4.2 Repository pattern
Each repo has a small interface (`EventsRepo.put / remove / byDay / byMonth …`) and one Dexie implementation. A write is **one Dexie transaction**: update the row and append to the outbox, then call `nudge()` on the sync host (§4.6). Screens use hooks (`useEventsOnDay(date)`) built on `useLiveQuery`, so every view, the calendar dots and Today update on their own (EVT-07, CAL-02).

The spec's "fixture repo first, API repo later" (spec §11) becomes a **transport swap**. Repos are always Dexie. The `Transport` interface covers every server call: `push`, `pull`, `weather`, `places`, `auth.*` (link, status, name, signout) and `upload(file, onProgress)`. `FixtureTransport` seeds the database with Appendix A data, accepts pushes without sending them, and simulates the rest with the spec's [Mock] delays and fixtures (place search, upload progress and failures, sign-in states). `HttpTransport` talks to the API. Screens don't change between Phase 2 and Phase 5.

**Code (S05, `data/repos/`).** `RepoProvider` takes a `RepoStore` = `{ db, accountId, account, now, startedAt, nudge, refreshWeather, photoSrc, upload, places, locate, signOut, markSignedOut }` (`locate` L05, `markSignedOut` H01) (`startedAt` and `refreshWeather` feed the zone states and "Try again", Y01 §4.4; `account` = `{ name, email }` of the signed-in account: `glance-meta` for a real display, Maria for the fixture; `useAccount()` reads it, for SET-01/08, V07); the shell builds it from the open account DB and the sync host (S06/S07), and tests inject one. Repos are `createXRepo(store)` (plain, testable) plus a `useXRepo()` hook that memoizes it from the provider. Writes (`outbox.ts`): `putQueued` / `removeQueued` run one `rw` transaction over the entity table and `outbox`, then call `nudge()` once it commits; a throw rolls back both. A put keeps the stored row's `updatedAt` / `version` (a new row gets `now` and version 0, the server stamps the real values) and queues the full row as the payload. A remove sets `deletedAt = now` on the local row (so hooks drop it at once) and queues a delete with no payload; removing an unknown id queues nothing. Repos: `EventsRepo.put(event) / remove(id)`, `NotesRepo.put(note) / remove(id)`, `SettingsRepo.update(change)` (merged over defaults and the saved row, queued as the whole row keyed by `accountId`). Photos have no outbox writes: uploads skip the outbox (§6.3). `PhotosRepo.upload(file, onProgress)` (I05) calls the store's `upload` (`Transport["upload"]`) and, on success, puts the returned `StoredPhoto` into `photos`, so `usePhotos()` picks it up at once; it answers the transport's `Result`. The fixture display wraps `FixtureTransport.upload` so a finished upload's `photoSrc` is an object URL of the chosen file (the demo has no file server); a signed-in display uses `HttpTransport.upload` (C01). Weather is written only by the sync engine. `WeatherRepo.searchPlaces(query)` (I07) answers the store's `places` (`Transport["places"]`): the fixture display passes `FixtureTransport.places`, a signed-in display passes `HttpTransport.places` (C01). Hooks (`useLiveQuery`, `undefined` while the first read runs, deleted rows filtered out, index order): `useEventsOnDay(dayKey, tz)` and `useEventsInMonth(year, month, tz)` (events whose `startAt` falls in the day or month in `tz`: `[dayStart(key, tz), dayStart(addDays(key, 1), tz))` and the same from the 1st to the next month's 1st, by start, L02); `useHasEvents()` (whether any live event exists, for CAL-04's empty calendar, V02); `useEvent(id)` (one live event, `null` when it is missing or deleted, for the edit sheet, V03); `useNote(id)` (the same for one note, V05); `useNotes(now)` → `ShownNote` = row + derived `pending` (has an outbox entry, OFF-04 "Waiting to post"), newest first (NOTE-04, V01), hiding notes past `noteExpiry` (NOTE-08, default settings when no row); `usePhotos()` (upload order, oldest first, TODAY-07; Photos reverses it, V06); `usePhotoSrc()` returns the store's `photoSrc(id, variant)` (V01): `RepoStore` carries it because `features` can't import `fixtures`, so `session.ts` gives the fixture display `fixturePhotoImage` (bundled SVGs, falling back to the API path) and a signed-in display `apiPhotoSrc` = `/api/photos/{id}/file?v={display|thumb|orig}`; `useSettings()` (saved row merged over `DEFAULT_SETTINGS`, defaults when no row); `useWeather()` (`null` when no forecast is saved). Range queries compare ISO strings, which works because every stored timestamp is UTC `toISOString()` form.

**Code (S03):** `data/sync/transport.ts` defines `Transport`. Every method returns `Promise<Result<T, TransportError>>` (`Result` in `domain/result.ts`), with `TransportError` = `network` (offline or unreachable) · `unauthorized` (401) · `invalid` (400/422) · `outdated` (426) · `server` (5xx, or the weather provider failing). `push(entry: OutboxEntry)` → `Change`; `pull(cursor | undefined)` → `{ cursor, changes: Change[] }`, where `Change` is `{ entity, row }` per synced entity with the full stored row (a delete answers with the tombstone row); `weather()` → `Weather`; `places(query)` → `WeatherLocation[]` (empty = unknown place, WX-08); `auth.link({ email, timeZone })`, `auth.status()` → `waiting | expired | finishing-elsewhere | signed-in { account, returning, setupDone }`, `auth.name(name)` → `Account`, `auth.location({ place } | { skip: true })` (L08), `auth.signout()`; `locate({ lat, lon })` → `WeatherLocation`, whose error adds `outside` (`LocateError`, L05; `Coordinates` = `Pick<WeatherLocation, "lat" | "lon">`), and `WeatherRepo.locate(coords)` passes it through like `searchPlaces` (`RepoStore.locate`); `upload(file, onProgress(percent))` → `StoredPhoto`, whose error adds `too-large | not-a-photo` (`domain/photoUpload.ts`, checked again by the server). Callers ignore a stale answer instead of cancelling it (WX-07 "typing cancels").

`data/sync/fixtureTransport.ts` (S03): `seedFixtureDb(db, params)` clears every table (outbox included) in one transaction and writes the Appendix A rows with fixed server fields (`updatedAt` = fixture now, `version` 1), the settings and weather rows under the fixture account id, and the `cursor` meta entry. `empty=1` seeds only default settings (no location) and the cursor; `wx=` seeds everything except the weather location and the forecast, so Weather opens on the setup card (V04); `net=loading` seeds nothing, so zones stay loading; `net=wxerror` leaves out the saved forecast; `bg=photo` seeds the background in Photo mode on the Appendix A photo (Cannon Beach, V07), also together with `wx=` (V10). A `now=` inside the default ambient hours seeds, and `weather()` answers, the Appendix A ambient forecast (56° light rain) instead of the morning one, so `/ambient?now=2026-10-09T19:12` matches the Ambient board (V08). `createFixtureTransport({ db, params, now })` is a fake server: a put answers with the payload stamped with `now` and the next version; a delete reads the local row and answers with it tombstoned (`invalid` if the store never had it); pull answers with no changes. Modes: `net=offline`, `signin=offline` and `upload=offline` fail every call with `network`; `net=loading` never answers pull or weather; `net=wxerror` fails weather with `server`. Mock delays: place search 1.2 s (WX-07), link 1.4 s (SIGNIN-03), upload progress +8 % every 400 ms. Place search matches the Appendix A places, then accepts any 5-digit ZIP or a query with a comma as one place (`name, region` split at the comma, coordinates 0/0, since fixture weather is always Portland). `locate` (L05) always answers `FIXTURE_LOCATED_PLACE` (Portland, OR at 45.52, -122.68, Pacific) after 2.6 s (`LOCATE_DELAY_MS`, the v4 prototype's wait), or `network` with `net=offline`. `auth.status` follows `signin=` (`phone` → `finishing-elsewhere`, `expired`, `done` → Maria signed in with `setupDone`, `returning` from `acct=returning`) and is otherwise `waiting`; `auth.location` always answers ok. `createFixtureSearch(params)` holds `places` and `locate`, so `/signin` uses them without a Dexie store (L08). `wx=` (beyond the seed) and the other `signin=`/`upload=` values are the screens' reducer initial states and don't change the transport.

**Code (C01):** `data/sync/httpTransport.ts` `createHttpTransport({ fetch, createXhr })` (both injectable for tests; defaults are the global `fetch` and `XMLHttpRequest`, so it runs in the page and the worker). Paths are same-origin: `push` → `PUT /api/{entity}/{entityId}` with the payload as JSON, or `DELETE` with no body, and answers `{ entity, row }` from the stored row; `pull` → `GET /api/sync` (`?since={cursor}` when there is one); `weather` → `GET /api/weather`; `places` → `GET /api/weather/places?q=` (URI-encoded); `auth.link` / `auth.name` → `POST` JSON, `auth.status` → `GET`, `auth.signout` → `POST`. Every request carries `X-Glance-Build: {CLIENT_BUILD}` (§4.5 Gap 6). Status mapping: 2xx → `ok` (204 → `undefined`); 401 → `unauthorized`; 426 → `outdated`; 5xx and 429 → `server`; any other 4xx (400, 403, 404, 409 `no-location`, 422) → `invalid`; a request that throws → `network`; a 2xx body that isn't JSON (a proxy page) → `server`. Bodies are trusted as typed (same build contract), not re-validated. `upload` runs `uploadProblem` first and answers `too-large` / `not-a-photo` without sending; otherwise it sends the raw file with XHR (§6.3: `Content-Type`, URI-encoded `x-file-name`, build header), reports `upload.onprogress` as a whole percent, maps 413 → `too-large`, 415 → `not-a-photo` and the rest as above, and answers `network` on `error`, `abort` or `timeout`. L05: `locate` → `GET /api/weather/locate?lat=&lon=` maps 404 → `outside` itself (the sender takes a status → error map), the way `upload` maps 413/415; the setup (L06) shows `outside` as that notice and every other error as `lookup`.

- **Never store derived values** (event status, counts, pending, hero state). Compute them.
- **Multi-state flows** (sign-in, upload tile, weather setup, sync status) are a discriminated union + a reducer. A URL fixture param is the reducer's initial state.
- **Services and the sync engine return `Result<T, ErrorCode>`** instead of throwing across boundaries.

**Zone state (LOAD-\*, FAIL-\*, OFF-\*).** Local reads don't fail, so a zone's state describes **freshness**, not the read. `zoneState()` in `domain` is a pure function of (local rows, ever synced, sync status, now). **Ever synced** = a pull cursor exists in `meta`, so it survives reloads:

| State | When |
|---|---|
| `loading` | No local rows, never synced, for up to 10 s (LOAD-02/03) |
| `failed` | No local rows, never synced, and the pull failed or took over 10 s (FAIL-01) |
| `empty` / `ready` | Ever synced, or local rows exist. Works offline after a reload. `ready` carries `updatedAt` when the last pull failed (FAIL-02) |

`zoneState({ rows, everSynced, failed, lastSyncedAt, timedOut })` returns `ZoneState<T>` = `{kind: "loading"} | {kind: "failed"} | {kind: "empty"} | {kind: "ready", data, updatedAt?}`; `updatedAt` is `lastSyncedAt`, set only when the last sync failed. `loadingTimedOut(since, now)` is the LOAD-03 rule (10 s, `LOADING_LIMIT_MS`). Weather uses its own `status.weather` (§4.6) instead of the pull: `weatherZone({ located, weather, failed, timedOut })` is `empty` without a location, `ready` with a saved forecast (`updatedAt` = its `fetchedAt` while the last fetch failed, FAIL-02), else `failed` when the fetch failed or timed out, else `loading`; `located: undefined` means the location isn't known yet (never synced and no settings row), which loads instead of showing the setup card. Every zone renders through `ZoneState<T>` + `<Zone>` and has its own error boundary.

**Wiring (Y01).** `data/repos/status.ts` `useSourceStatus()` = `{ everSynced, failed, lastSyncedAt?, retryAt?, since, weather }`: `everSynced` = a pull cursor in `meta`; `failed` = the last sync failed (`error` set, or `online: false`); `since` = `RepoStore.startedAt` (the shell clock when the display opened its store), so a zone's 10 s count starts once per boot, not per view. `useRetry()` = `{ sync, weather }` → `RepoStore.nudge` / `RepoStore.refreshWeather` (the host's; no-ops outside demo builds until C02). `shell/sourceZone.ts` turns them into `SourceZone<T>` = `{ state, retryIn, retry }`: `useSyncedZone(rows | undefined)` (a local read still running is `loading`) for events, notes and photos, and `useWeatherZone(weather, located)`, whose 10 s count starts at `status.weather.since` while a fetch runs, at `since` before the first sync, and doesn't run otherwise (a location picked later waits for its own fetch). The timeout is a `useSyncExternalStore` boolean over the now store, so a zone re-renders once when it flips, not every second; under a frozen `?now=` it never flips, so `net=loading` frames stay on their skeletons. `retryIn` = `retryMinutes(retryAt, now)` at minute granularity (1 when no retry is scheduled yet, e.g. after a timeout). Each failing zone shows `SourceFailure`: "{Source} unavailable", `copy.zone.failedBody(n)` (weather keeps `copy.weather.failed.body(n)`) and "Try again" → `retry`. A ready zone with `updatedAt` appends " · Updated {time}" (clock format) to its count eyebrow (Today schedule and notes, Calendar day, Notes board, Photos "Family photos · {n}") or to the weather location (Today tile, "{location} · Now"). Exceptions: on Calendar failure the Today hero shows only the clock (no "Nothing scheduled"), Picture of the day renders nothing, the Background grid has no count to mark, and Ambient keeps both zones blank on failure because the whole screen is the wake button (a nested "Try again" would be invalid); its retries run on their own. `ui/Zone.tsx` is a `"use client"` module because its error boundary is a class component and feature indexes reach it from server page files.

### 4.5 Offline boot and caching
A signed-in screen must cold-start offline (after a reload or a power cut) with every view working.

**Gap 1: offline navigation (must-fix before Phase 5).** App Router soft navigation fetches RSC payloads even for `'use client'` pages.
- Every `(app)` route, `/ambient` and `/signin` is **fully static**: no `cookies()`, `headers()` or server data, and auth gating happens on the client. `?date=` is read with `useSearchParams` inside a Suspense boundary.
- The SW caches their HTML when it activates, and RSC payloads as they're fetched (C04, below). At runtime, NetworkFirst (3 s) handles navigations and requests with the `RSC: 1` header, matched by pathname with the `_rsc` query ignored. A navigation that misses the cache falls back to `/today`.
- The shell prefetches all six views on startup (`router.prefetch`).
- `/` → `/today` is a `redirects()` entry in `next.config`, not a server component, so it stays static.

**Gap 2: auth bootstrap offline (must-fix).** The session cookie is httpOnly, and `glance-{accountId}` is only found through its own meta table.
- `data/meta.ts` keeps `{accountId, name, email}` in a small **`glance-meta`** Dexie DB, written after sign-in. Name and email let Settings render offline (SET-01, SET-08). Code (S02): one table `account` keyed by `accountId` holding at most one `SignedInAccount` (`name` is `null` until named, as in `Account`). `openMetaDb()`, `readSignedInAccount(db)`, `saveSignedInAccount(db, account)` (clears and puts in one transaction, so a different account replaces the old entry), `clearSignedInAccount(db)` and `deleteMetaDb()`.
- Offline: trust it and open `glance-{accountId}`. No entry → `/signin`.
- Online: a 401 from any call means signed out (Gap 3).

**Gap 3: 401 handling (must-fix).** See the push errors in §5. If a different account signs in afterwards, the old account DB is deleted along with its pending writes. **Code (C03):** `SignInAuth.remember(account)` (`data/repos/session.ts`) reads the `glance-meta` entry first; when it names another account it deletes that account's data (`deleteAccountData`: its Dexie DB and the `photos` cache) before saving the new entry, so a crash in between leaves no orphan DB. The same account keeps its DB and outbox, which the worker then pushes (SIGNIN-13).

**Signed-out screen (H01, SIGNIN-13 from handoff v4).** On the worker's `unauthorized` (`useSignedOut()` in `data/repos/status.ts`, the sync status error), `SessionGuard` calls `RepoStore.markSignedOut()`, which sets `signedOut: true` on the `glance-meta` entry (`meta.ts` `markSignedOut`; kept, with the email, so a reload still shows the notice; `remember()` drops it because `saveSignedInAccount` replaces the entry when any sign-in finishes). The fixture display's `markSignedOut` does nothing. Nothing else stops the worker: the engine already halts on `unauthorized` and pushes nothing more, so saves made meanwhile stay in the outbox. Once the entry is written, `SessionGuard` (inside `SheetHost` and `IdleProvider`) routes to `/signin` only when nothing is being edited: no sheet open and no text field focused (it follows `focusin`/`focusout`); otherwise it waits for the sheet to close or the field to lose focus, or for the idle timeout. While signed out, `IdleProvider` sends the idle timeout to `/signin`, or to `/ambient` during ambient hours, and the schedule end leaves `/ambient` for `/signin`; it doesn't close the sheet itself then, since the route change discards it (`SheetHost`), so `SessionGuard` never sees the sheet close before the path changes. On `/ambient` `SessionGuard` doesn't route: `AmbientScreen` shows "Signed out · tap to sign in" in the OFF-05 slot, and its wake tap goes to `/signin` (AMB-05, AMB-07). A screen already on `/signin` stays there when ambient hours start (`/signin` has no `IdleProvider`). **Boot:** `useDisplayBoot` answers `signed-out` for an entry with `signedOut: true` and starts no worker, so a reload (online or offline) opens the form instead of drawing another 401. **On `/signin`:** `data/repos/session.ts` `signedOutAccountFor(demo, params)` reads the entry and, when it is signed out, opens `glance-{accountId}` once (only if it exists) to read the outbox count and the settings, then closes it → `SignedOutAccount {email, pending, settings?}`; in demo builds it comes from `signin=ended` and `pending={n}`. `SignedOutProviders` waits for it, spreads its settings under the fixture overrides in `DefaultSettingsProvider` (so the clock, season and `TimeZoneProvider` follow the account) and provides it through `SignedOutAccountProvider`. **Form:** the notice must outlive every step until a sign-in finishes (a failed send, "Use a different email", an expired link), so it is not a reducer step: `SignInScreen` reads `useSignedOutAccount()`, `initialSignIn` opens the `form` step with its email (`switch=1` enters `sam.lee@example.com` instead), and `SignInView` takes `signedOut {email, pending}`: the soft banner, "Sign in again", no "Continue as guests", and the different-email tile when `isSwitchingEmail(previous, draft, pending)` (`domain/signIn.ts`: changes waiting and a non-empty trimmed, lower-cased draft that differs), whose "Use {email}" dispatches the `email` action. Nothing derived is stored. Fixtures: `signin=ended`, `pending={n}`, `switch=1`, and `signin=ended` on display routes (e.g. `/ambient?signin=ended`, `/today?signin=ended&sheet=newnote`), where the fixture transport answers push and pull with `unauthorized` and the forecast as saved. Demo navigations drop fixture params, so from there the wake tap or a closed sheet opens the plain form.

**Gap 4: photos offline (recommended).** After each pull (and once at start, for every live photo already saved, C04), the sync worker sends `photosChanged(ids)` to the page, and the page forwards them to the SW. The SW fetches the `thumb` and `display` variants into a CacheFirst `photos` cache (ExpirationPlugin, ~300 entries). The background, slideshow and picture of the day then work offline even for photos never viewed on that screen.

**Gap 5: storage eviction (recommended).** Call `navigator.storage.persist()` after sign-in (C03: `remember` calls it once `glance-meta` is saved, when the browser has `navigator.storage`; the answer and any error are ignored, since a refusal only means the browser's own eviction rules apply). On iPad kiosks, install as a home-screen app (manifest: `display` fullscreen/standalone, `start_url` `/today`, icons). Installed apps are exempt from Safari's 7-day storage cap. **Manifest (S08):** `app/manifest.ts` serves `/manifest.webmanifest`: `display: fullscreen` (browsers that lack it fall back to `standalone`, as iPadOS Safari does), `start_url` `/today`, `id` and `scope` `/`, `background_color` white and `theme_color` black (the canvas and inverse surfaces). Icons in `public/icons/`: 192 and 512 px PNGs (`any`; the 512 is also listed as `maskable`, since the glyph sits inside the 80 % safe zone) and a 180 px `apple-touch-icon`. There's no logo yet, so the icon is a white Geist 540 "G" on black, following the DS rule of setting the product name in Geist where a mark would go. The root layout's `metadata` links the favicon and apple-touch icon and sets `appleWebApp` (capable, title `copy.appName`) for the iPad home screen. The SW (C04) precaches these files.

**Gap 6: updates on an always-on screen (recommended).** A new SW waits instead of taking over. Once `IdleProvider` reaches Ambient or Today-idle **and the outbox is empty** (no `outbox` rows, read with `useLiveQuery`), `IdleProvider` sends `SKIP_WAITING` and reloads once on `controllerchange` (C04). Push endpoints stay backward-compatible. The client sends its build id, and the server answers incompatible clients with **426**. **After a 426 the outbox can't drain**, so the empty-outbox condition is dropped: the update applies at the next idle with entries still pending. They survive the reload in IndexedDB and the new version pushes them. **Build check (B03):** the client sends `X-Glance-Build: {CLIENT_BUILD}` (`domain/build.ts`, a whole number bumped only when a change breaks the push contract, not on every build; C01 adds the header). Entity writes answer `426 {error: "outdated"}` when the header is missing, not a whole number, or below the server's `MIN_CLIENT_BUILD` (`server/http.ts`; H02 raised `CLIENT_BUILD` and `MIN_CLIENT_BUILD` to 2, so a build-1 client that writes `ambientHours` gets 426). B04 applies the same check to `/api/sync`. **Page side (C02):** `IdleProvider` reads `useSyncStatus()`; while `error` is `outdated`, every idle move (the idle timeout, or entering or leaving Ambient on the schedule) loads the target path in full (`window.location.assign`, injectable as `reload` for tests) instead of `router.push`, even when already on it, so the next idle brings in the new version with the outbox kept. A new page load drops the stale `outdated` with the `restarted` status event (§4.6). C04 replaces the plain load with the `SKIP_WAITING` flow above when a new SW is waiting; the plain load stays the fallback when none is (no SW support, or the update not found yet).

**Code (C04).** `@serwist/turbopack` 9.5.13 with native `esbuild` 0.28.2 (both exact pins; `withSerwist` in `next.config.ts` keeps esbuild out of the server bundle).
- **Build:** `app/serwist/[path]/route.ts` `createSerwistRoute({ swSrc: "app/sw.ts", useNativeEsbuild: true, esbuildOptions: { format: "iife" }, globPatterns, additionalPrecacheEntries })`. The precache manifest is `.next/static/**/*.{js,css,woff2,png,svg,ico,webp}` (Next's default glob misses `woff2`, so the Geist fonts are listed explicitly), `public/**/*` and `/manifest.webmanifest` (revision: a UUID made at build time, so every build ships a new SW). The output is an IIFE and the page registers it as a **classic** script (`type: "classic"`), so browsers without module service workers run it too.
- **Route HTML and RSC aren't in the precache manifest.** The manifest can't send the `RSC: 1` header, and Next 16 prefetches per segment (`Next-Router-Segment-Prefetch: /_tree`, then the page segment), so the payloads aren't single files. Instead the SW, on `activate`, fetches every `OFFLINE_PAGES` path (the nine static pages; a test compares the list with `app/**/page.tsx`) into the `pages` cache, keyed by path. RSC responses land in `pages-rsc` keyed by path + the segment header (`prefetch` or `full` without one), `_rsc` ignored (`rscCacheKey`), max 64 entries. The shell's startup `router.prefetch` of the six views fills it on the first controlled load. A soft navigation whose payload isn't cached falls back to a full load, which the `pages` cache serves.
- **Runtime routes** (`app/sw.ts`, first match wins): photo files `/api/photos/{id}/file` → CacheFirst `photos` (ExpirationPlugin, 300 entries); every other `/api/*` → NetworkOnly; `RSC: 1` → NetworkFirst 3 s `pages-rsc`; navigations → NetworkFirst 3 s `pages` keyed by path (query ignored), falling back to the cached `/today`; `/_next/static/*` not in the precache (a newer build's chunks fetched while the old SW still controls the page) → CacheFirst `assets` (256 entries). `skipWaiting: false`, `clientsClaim: true` (so a skip-waiting SW takes the page and fires `controllerchange`), `cleanupOutdatedCaches`.
- **Worker bootstrap:** Turbopack starts the sync worker as `turbopack-worker-*.js#params=…` and reads its config from the worker's own URL. A cached response keeps the URL it was cached under, so the worker loses the `#params` and dies ("Missing worker bootstrap config"). A `cachedResponseWillBeUsed` plugin on the precache and `assets` routes rebuilds the response (`new Response(body, cached)`), which has no URL, so the browser uses the request's.
- **Photo warming:** `createSyncEngine({ …, photosChanged })` reports the live photo ids each pull brought in, and on `start()` every live photo already saved (so a screen that synced before C04, or whose cache was evicted, warms too). The worker passes it to `page.photosChanged`; `createWorkerSyncHost({ db, spawn, photosChanged })` adds it to the Comlink proxy; `openAccountDisplay` wires it to `appServiceWorker().warmPhotos`, which posts `{ type: "WARM_PHOTOS", ids }` to `navigator.serviceWorker.ready`'s active worker. The SW runs each `thumb` and `display` URL through the same CacheFirst strategy, one at a time, so cached files cost nothing and a home server isn't flooded.
- **Registration and updates:** `shell/ServiceWorker.tsx`, rendered by the root layout, calls `appServiceWorker().register()` once: `/serwist/sw.js`, scope `/`, `updateViaCache: "none"`, then `registration.update()` every hour (`UPDATE_CHECK_MS`), since a kiosk rarely navigates and the browser only checks on navigations. `appServiceWorker()` is inert in `next dev` and without `navigator.serviceWorker`. `IdleProvider` takes `updates` (`updateWaiting`, `applyUpdate`, `checkForUpdate`; injectable for tests) and reads `useOutboxEmpty()` (`data/repos/status.ts`, the `outbox` count by `useLiveQuery`). On each idle move: a waiting SW and (an empty outbox or `outdated`) → `applyUpdate(() => reload(path))`, which posts `SKIP_WAITING` once and loads the target path on the next `controllerchange`; otherwise `outdated` → the plain load (C02); otherwise `router.push`. A 426 (`outdated`) also calls `checkForUpdate()` right away, so the new SW is usually waiting by the next idle.

|---|---|---|
| Static assets (`/_next/static/*`, fonts, icons, manifest) | Precache | Hashed and immutable. Needed for a cold start |
| Route HTML (navigations) | Cached on SW activate + NetworkFirst 3 s → cache → `/today` | Fresh when online, instant when offline |

### 4.6 Sync worker
**Split.** The page reads through hooks, writes through repos, then calls `nudge()`. The worker owns:
- the outbox drain,
- pull-since-cursor + apply, skipping rows still in the outbox,
- the `EventSource` on `/api/sync/stream` with the 30 s polling fallback,
- backoff, the `glance-sync` lock, and weather: a refresh every 15 min, right after a sync leaves a new `weatherLocation` known to the server (pulled from another screen, or picked here and pushed, I07), and on `refreshWeather()`. Failed fetches retry on the FAIL-03 schedule (1, 2, 5 min, then every 5).

Both contexts open the same Dexie DB. Dexie 4 broadcasts changes across contexts, so page `liveQuery` hooks update by themselves. **The worker never posts data to the page**, only `photosChanged` and `restart`. Status lives in `meta`.

**Messages** (typed, Comlink). The page passes its callbacks to `start` with `Comlink.proxy`. **Status is not a message:** the active worker writes it to `meta`, so every tab sees the same status with no relay.

| Direction | Message |
|---|---|
| page → worker | `start(accountId, page)`, `nudge()`, `resync()`, `refreshWeather()`, `stop()` (the page host terminates the worker instead) |
| worker → page | `photosChanged(ids)`, `restart()` |
| worker → Dexie `meta.status` | `{ online, lastSyncedAt?, error?: 'unauthorized' \| 'server' \| 'outdated', weather: { state: 'idle' } \| { state: 'loading' } \| { state: 'failed', retryAt } }`. Every tab reads it with `useLiveQuery`. Derived values aren't stored: "ever synced" is the `cursor` meta entry (§4.4) and the pending count is the `outbox` table |

**Code layout** (`src/data/sync/`, §3):
- `engine.ts` holds all the logic and runs anywhere.
- `sync.worker.ts` hosts it in the worker.
- `host.ts` spawns it with `new Worker(new URL('./sync.worker.ts', import.meta.url), { type: 'module' })` and wraps it with Comlink. If `Worker` is unavailable, `host.ts` runs `engine.ts` inline behind the same API.
- **Fixture mode** spawns no worker: the engine runs inline with `FixtureTransport`.

**Rules**
- **Errors:** the §5 push rules run in the worker. On 401 it sets `error: 'unauthorized'` in the status, stops syncing and keeps the outbox, and the page routes to `/signin` (from H01 it marks the screen signed out and waits for open edits, §4.5 Signed-out screen). On 426 it sets `'outdated'` and the page applies the waiting update at the next idle, even with pending entries (§4.5 Gap 6).
- **Schema upgrades:** the worker handles `db.on('versionchange')` by closing Dexie and posting `restart`. The page terminates the worker and respawns it after its own DB upgrade. The worker must never block an upgrade.
- **Photo warming:** the worker posts `photosChanged(ids)`, and the **page** forwards them to the SW. The worker never touches `navigator.serviceWorker`.
- **No cached outbox:** the worker re-reads the outbox on every drain, with no in-memory copy.
- **One active worker per browser:** each tab spawns a worker, but only the holder of the `glance-sync` lock pushes, pulls, holds the SSE stream and refreshes weather. Other workers wait on the lock, and a `nudge()` in their tab reaches the active worker through the outbox write itself (Dexie change broadcast).

**Code (S04).** `data/sync/engine.ts`: `createSyncEngine({ db, transport, accountId, now })` → `{ start, nudge, resync, refreshWeather, stop }`; every call but `stop` returns `Promise<Result<void, TransportError>>`. `nudge()` = drain the outbox (re-read by `seq` before each push, one push at a time), then pull since the cursor. Runs go through one serial queue, so overlapping nudges never push an entry twice. `resync()` is the same with a pull from scratch (no cursor). `start()` runs a sync, then a weather refresh unless the pull already triggered one. Push answers and pulled rows are written only when the row has no outbox entry left (same transaction as the entry removal or the cursor write); tombstones are saved as rows with `deletedAt`. Push errors per §5: `invalid` drops the entry, deletes the local row if no other entry is pending and makes the next pull start from scratch, which restores the server's copy; `unauthorized` / `outdated` (on push, pull or weather) keep the outbox, record the error and halt the engine (every later call answers the same error until a new engine starts); `network` / `server` keep the entry, add 1 to its `attempts`, stop the drain, and the pull still runs. Weather: skipped while settings have no `weatherLocation`; success saves `{ ...weather, accountId }` and schedules the next refresh in 15 min (WX-06); a failure schedules a retry by `domain/retry.ts` `retryDelayMs(failures)` (1, 2, 5, then every 5 min, FAIL-03) and records `retryAt`; success resets the count. After every sync (I07) the engine refreshes weather right away when the saved location's coordinates differ from the ones it last fetched for and no `settings` entry is waiting in the outbox, so a location pulled from another screen, or picked here once its push is accepted, loads at once, and the server never fetches for a place it hasn't saved yet. `data/sync/status.ts` holds the `SyncStatus` union, `STATUS_KEY` (`status`) and the `nextStatus(status, event)` reducer (`synced` · `failed` · `weather-loading` · `weather-loaded` · `weather-failed`); the engine writes it to `meta` in a transaction. A network failure sets `online: false`; any other failure sets `error`; a sync clears `error` and `retryAt` and sets `lastSyncedAt`. **Retries (Y01):** a failed sync that doesn't halt schedules another `nudge` by `retryDelayMs(failures)` (1, 2, 5, then every 5 min, FAIL-03) and records `retryAt` with the `failed` event; any sync (including a manual nudge) cancels the pending retry first, and a successful pull resets the count. `weather-loading` carries `at`, stored as `weather: { state: "loading", since }`, so the weather zone can time out (LOAD-03). `data/sync/host.ts` has `createInlineSyncHost({ db, transport, now })` → `{ start(accountId), nudge, resync, refreshWeather, stop }`, which runs the engine in the page (fixture mode and the no-`Worker` fallback); calls before `start` do nothing. SSE, the 30 s polling, push backoff, the `glance-sync` lock and the worker are C02 (below). `retrying()` answers whether a failed sync is waiting on its FAIL-03 retry (C02).


**Code (C02).** `data/sync/worker.ts` `createSyncWorker(deps)` → `{ start(accountId, page), nudge, resync, refreshWeather, stop }`, with `deps` = `{ openDb, transport, now, locks, openStream, events }` so tests inject fakes; `liveWorkerDeps(events)` gives the real ones (`glance-{accountId}`, `createHttpTransport()`, `navigator.locks`, `EventSource` when it exists, the global scope for `online`). `sync.worker.ts` only `expose`s it with Comlink. `start` opens the account DB and asks for the `glance-sync` lock (`navigator.locks.request` with an `AbortSignal`; with no Web Locks it goes straight on). Only the holder creates the engine and runs `start()`, then: (1) watches the outbox with `liveQuery` and nudges when an entry with a higher `seq` than any seen appears, so a write from any tab reaches the active worker through Dexie's change broadcast; (2) opens `EventSource('/api/sync/stream')` and nudges on each ping and when the stream reopens after a drop (not on the first open, since `start` just pulled, unless that start failed and waits on its FAIL-03 retry: after an offline cold start the stream's first open is the reconnect, so it pulls and pushes at once, Q01); (3) every 30 s (`POLL_MS`) nudges if the stream isn't open **and** the engine isn't `retrying()`, so polling never cuts the FAIL-03 backoff short; (4) nudges on the `online` event. A waiting worker keeps no engine, so its `nudge` / `resync` / `refreshWeather` do nothing. `stop` aborts the signal (lock released or the wait dropped, stream closed, polling cleared, engine stopped) and closes the DB. `db.on("versionchange")` runs the same stop and calls `page.restart()`. Relative URLs resolve against the worker script, which is same-origin, so `start` takes no `apiBase`. `photosChanged` is passed to the engine (C04, §4.5). Page side, `host.ts`: `spawnSyncWorker()` = `new Worker(new URL("./sync.worker.ts", import.meta.url), { type: "module" })` wrapped with Comlink, or `createSyncWorker(liveWorkerDeps(window))` in the page when `Worker` is missing; `createWorkerSyncHost({ db, spawn, photosChanged })` implements `SyncHost`: `start` spawns and calls `start(accountId, proxy({ restart, photosChanged }))`, `stop` terminates the worker (which drops its lock and connections), calls before `start` or after `stop` do nothing, and `restart` terminates the worker, waits for the page's own `db.open()` (its upgrade) and spawns a new one on the same account. A failed `db.open()` (this page's code is older than the DB) leaves it stopped. **Status across sessions:** `status.ts` `recordStatus(db, event)` (also used by the engine) and the `restarted` event, which drops an `unauthorized` or `outdated` error (a halt belongs to the engine that hit it) and keeps the rest; `openAccountDisplay` records it before rendering, so a stale halt from the last session never redirects or reloads a fresh page. **401 in the page (SIGNIN-13):** `shell/SessionGuard.tsx`, inside `RepoProvider` in `DisplaySession`, calls `router.replace("/signin")` when `useSyncStatus().error` is `unauthorized`; the outbox stays in the account DB. **426** is handled at the next idle by `IdleProvider` (§4.5 Gap 6).

## 5. Sync protocol

Everything in this section runs in the sync worker (§4.6).

**Push (client → server).** The engine drains the outbox in `seq` order, one request at a time:
`PUT /api/{entity}/{id}` (full row, idempotent upsert) or `DELETE /api/{entity}/{id}`. 2xx → remove the entry, then save the returned row (with the server `updated_at`/`version`) **only if no other outbox entry remains for that row**. Otherwise a newer local edit made during the request would be overwritten. Errors:
- **401** → keep the outbox, stop syncing, route to `/signin` (§4.5 Gap 3; from H01 once nothing is being edited, §4.5 Signed-out screen).
- **400/422** → drop the entry, revert the row from the server (or delete it locally if the server never had it), log it. This should never happen after client validation.
- **426** → keep the outbox, stop syncing, apply the waiting update at the next idle (§4.5 Gap 6).
- **404** (a `DELETE` for a row the server never had, or an id that belongs to another account) → treat as 400 (`invalid`; `HttpTransport` maps it, C01).
- **Network error / 5xx** → keep the entry and retry with backoff, and on reconnect.

**Pull (server → client).** Every write on the server bumps a global `version` (one counter table, incremented in the same transaction). `GET /api/sync?since={cursor}` returns `{ cursor, changes: [{entity, row}] }`, tombstones included. The client applies the changes in one transaction and **skips rows that have a pending outbox entry**, so a local edit isn't overwritten before it's pushed.

**Conflict rules** (refine SYNC-03):
- **Delete wins.** A `PUT` on a tombstoned row doesn't bring it back. The server returns the tombstone with 200, and the client applies it.
- **Settings are one row.** The last write replaces the whole JSON, so two screens changing different settings at the same moment lose one change. This is rare and accepted for v1.

**Triggers.** `GET /api/sync/stream` (SSE) sends `{version}` when the account changes. The `server/bus` EventEmitter fans out writes to the account's open streams, with a heartbeat every 25 s. If there's no SSE, the client polls every 30 s. A pull also runs on app start, on reconnect and after each push. Client side (C02, §4.6): a ping or the stream reopening nudges; while the stream isn't open (no `EventSource` in the worker, or a dropped connection) the worker polls every 30 s unless a failed sync is waiting on its FAIL-03 retry; the `online` event nudges at once.

**As built (B04).** `GET /api/sync?since={n}`: build (426) → session (401) → cursor (400 unless absent or a whole number) → `pullChanges`. In one read transaction it returns the account's events, notes, photos and settings with `version > since` (all of them with no cursor), tombstones included, sorted by `version`, and `cursor` = the global `sync_state.version` as a string. Rows have the push answer's shape (`Synced<T>`, settings with `accountId`); a photo's `updatedAt` is its `created_at`, and a photo with no `taken_on` is dated by its upload day (PHOTO-03). `GET /api/sync/stream`: session (401) → `text/event-stream` (`Cache-Control: no-cache, no-transform`, `X-Accel-Buffering: no`). Every accepted write (the service index calls `announce`) publishes the row's version to the account; each open stream sends it as `data: {"version":n}`, and a `: heartbeat` comment every 25 s keeps proxies from closing it. Nothing is sent on connect: the client pulls on start and on reconnect. The stream has no build check, because `EventSource` can't send the build header; its pings carry no data, and the pull that follows does the check. The bus lives in one process, which D17 guarantees.

**As built (P02): versions commit in order.** Pull's cursor is only safe if no write can commit a version below a cursor a client has already seen. Each write transaction takes the `sync_state` row lock **first**: `stamp()` (`UPDATE sync_state SET version = version + 1 … RETURNING`) when the write always happens (settings, photo insert), else `lockVersions()` (`SELECT … FOR UPDATE`) before reading the row it may change, then `stamp()` once it writes (event and note put/delete, `saveLocation`, note expiry). So write transactions run one at a time from their first statement to their commit: version *n* is committed before *n + 1* is handed out, and a concurrent put and delete of one row can't both read it alive (delete still wins). A write that changes nothing (a tombstone replay, a 404) releases the lock without bumping the version. `pullChanges` runs in one `REPEATABLE READ` transaction, so the rows and `sync_state.version` come from one snapshot: every version up to the cursor is either in the answer or belongs to another account. `tech§5` test: concurrent puts get distinct versions and each concurrent pull answers exactly versions 1…cursor.

Photos: the metadata syncs this way. Files are warmed into the service worker's `photos` cache after each pull (§4.5 Gap 4). Uploads skip the outbox (§6.3).

## 6. Server design

### 6.1 Route handler shape
Each handler sets `export const runtime = 'nodejs'` and does four steps: `requireDisplay(req)` → `v.parse(Schema, body)` → service call → `Response.json`. Errors map to `{ error: code }` with 400/401/403/404/409/426/429/502 (403 a failed Origin check, 429 `rate-limited`, 502 `mail-failed`). Next middleware is **not** used for auth: the session check reads the database, which stays behind the services. Helpers live in `server/http.ts` (B02), and handlers import services from `@/server/auth` (or later service indexes), never `server/db`. Request schemas (`LinkRequestSchema`, `NameRequestSchema`) are in `domain/schemas.ts` with the other contracts.
- Mutating routes also check that `Origin` matches `APP_URL` (CSRF defense on top of `SameSite=Lax`).
- **Entity writes (B03).** `PUT /api/{events|notes}/{id}` and `DELETE /api/{events|notes}/{id}`, `PUT /api/settings/{accountId}`. Order: Origin (403) → build (426) → session (401) → body (400) → service (404). The body is the domain schema (`CalendarEventSchema`, `NoteSchema`, `AccountSettingsSchema`); Valibot strips the client's copy of `updatedAt`/`version`/`deletedAt`, and an event or note whose `id` differs from the path is 400. Each write runs in one transaction that bumps `sync_state.version` and stamps the row with it and `updated_at` = server now; the answer is the stored row (`Synced<T>`, plus `accountId` for settings), which is the push's `Change.row`. A `PUT` upserts. A `DELETE` sets `deleted_at` = `updated_at` = now and keeps the content. **Delete wins:** a `PUT` or a repeated `DELETE` on a tombstone answers the tombstone unchanged, with no version bump. A `DELETE` for an unknown id, or any write to an id owned by another account, answers 404 `not-found` and changes nothing; settings answer 404 unless the path id is the session's account. Settings have no `DELETE` (the row has no `deleted_at`, and the client never deletes it). Tones are stored as text (`'1'`…`'4'`, `soft`, `accent`) and read back as numbers or names. Note expiry (B07) is a job, not part of these services (§6.4). Each accepted write is announced on the sync bus (B04, §5).
- **Sync reads (B04).** `GET /api/sync` and `GET /api/sync/stream` are reads: no Origin check. See §5.
- **Photos (B05).** `POST /api/photos`: Origin (403) → build (426) → session (401) → `x-file-name` header (400) → service, which answers 201 with the stored row (`Synced<Photo>`), 413 `too-large` or 415 `not-a-photo`. `GET /api/photos/{id}/file?v=display|thumb|orig`: session (401) → variant (400) → the account's photo (404) → the file. No build check, because an `<img>` can't send headers. See §6.3.
- **Weather (B06).** `GET /api/weather`: build (426) → session (401) → `accountWeather` → the `Weather` row the worker saves to Dexie, 409 `no-location` when the account has no place yet, 502 `weather-failed` when Open-Meteo fails. `GET /api/weather/places?q=`: build (426) → session (401) → query (400 when missing or blank) → `WeatherLocation[]` (empty when nothing matches, WX-08), or 502 `weather-failed` (WX-07). Both are reads: no Origin check. See D13.
- **Location.** `GET /api/weather/locate?lat=&lon=` (L05, built): build (426) → session (401) → query (`readCoordinates`, 400 when either is missing, blank, not a number or out of range) → `locatePlace` → `WeatherLocation` with `timeZone`, 404 `not-found` outside the United States, 502 `weather-failed`. `POST /api/auth/location` (L08, built, SIGNIN-14): Origin (403) → build (426) → session (401), via `syncWriter` → body `LocationRequestSchema` = `{ place: WeatherLocationSchema } | { skip: true }` (400) → `finishLocationStep(accountId, step)` → 204 for both. In `services/settings.ts`, `saveLocation(deps, accountId, place)` merges the place into the account's settings row (or `DEFAULT_SETTINGS`) and stamps the next version; `finishLocationStep` runs it for a place and `finishSetup(deps, accountId)` (`server/auth/account.ts`: sets `accounts.setup_done_at` = now only when it is unset) in one transaction, and the services index announces the new version on the bus, so the screen's sync pulls the place like any settings write. A skip writes nothing else and bumps no version.
- **TPK-07 "same day"** is a client rule (the screen's local day). Timestamps are stored as UTC, so the server only checks `endAt > startAt` and `endAt − startAt < 24 h`.

### 6.2 Auth flow (SIGNIN-*)
1. `POST /api/auth/link {email, timeZone}`: void older links for the email, store `sha256(token)` with a random `pending_id` and the IANA `timeZone`, send the email. The waiting screen gets `pending_id` in a `pending` cookie. The response is the same whether or not the account exists.
2. `GET /api/auth/verify?t=…` (the link): check unused and < 10 min, mark used, create the account if new (`time_zone` from the link row), then create a display + session for **the opening device** and for the **waiting screen** (found by `pending_id`). Display rows are created only here, once the account exists. New account → name step on the opener (SIGNIN-06).
3. `GET /api/auth/status` (waiting screen, 2 s poll): `waiting | expired | finishing-elsewhere | signed-in{account, returning, setupDone}` → sets the session cookie once it's signed in.
4. `POST /api/auth/signout`: delete this display's session only (SIGNIN-11).
5. L08 (built): after the name step of a new account, `POST /api/auth/location` saves the SIGNIN-14 place or the skip (§6.1). The `timeZone` sent with the link stays the account's fallback zone. Either ends the first setup: `002_setup_done.sql` adds `accounts.setup_done_at` and fills it from `created_at`, so existing accounts are done. From L08 the waiting screen claims its session only once the account has a name **and** `setup_done_at`; until then status answers `finishing-elsewhere` (renamed from `needs-name-elsewhere`, same SIGNIN-07 screen). `signed-in` carries `setupDone`, so a device signing in to an account whose step never ended (a phone closed mid-step) shows SIGNIN-14 before Welcome.

Session cookie: `HttpOnly; Secure; SameSite=Lax`, no expiry in v1 (spec non-goal). Rate limit `auth/link` per email and per IP (in memory).

**As built (B02).**
- `POST /api/auth/link` (Origin check) → 204 + `pending` cookie. The email is trimmed and lowercased. Limits: 5 per email and 20 per IP per 10 min (fixed window, in memory, reset on restart) → 429. The IP is the last `X-Forwarded-For` entry (the one the HTTPS proxy appends), else one shared `unknown` bucket. "Voids older links" deletes that email's **unused** rows; a used row stays until its waiting screen claims it. A failed send → 502 (SIGNIN-03).
- `GET /api/auth/verify?t=` → 303 to `/signin?link=opened` with a `session` cookie, or `/signin?link=stale` (unknown, used, voided or ≥ 10 min old). For a stale link whose row still exists, a `link_email` cookie carries its email so the SIGNIN-12 screen can offer "Send a new link". On success it marks the row used, creates the account if new, then a display + session for the opener. If the opener also holds this link's `pending` cookie it is the waiting screen itself: one display, the row is deleted and `pending` cleared.
- The waiting screen's display + session are made on its first status poll **after** the name exists (the raw token can only be handed out then), dated at the link's `used_at`, and the link row is deleted so a `pending` id signs in once.
- `GET /api/auth/status` reads, in order: a valid `session` → `signed-in{account, returning, setupDone}` (`name: null` tells the opener to show SIGNIN-06, `setupDone: false` SIGNIN-14); else the `pending` row → `waiting`, `expired{email}` (unused and 10 min old), `finishing-elsewhere` (used, account unnamed or `setup_done_at` unset) or `signed-in` with a new `session` cookie; else `expired` (with `email` from `link_email` when present). `returning` = the account existed before this session's sign-in. Signed in clears `pending` and `link_email`.
- `POST /api/auth/name {name}` (Origin, session) saves the trimmed name (≤ 100 chars) to the session's account and returns the `Account`. `POST /api/auth/signout` (Origin) deletes this display's sessions and its display row and clears the cookie; it answers 204 with or without a session.
- `requireDisplay` resolves the `session` cookie to `{displayId, accountId}` and stamps `displays.last_seen_at`.

### 6.3 Photos
`POST /api/photos` takes one file per request, sent with **XHR so the progress bar is real** (fetch can't report upload progress). The size and type checks run in the client first and again on the server. The server streams the file to disk, `sharp` makes the display and thumb copies, then it inserts the row and bumps the version. Metadata: `title` = file name without the extension, `taken_on` = EXIF date or else the upload date, `place` empty (the eyebrow then shows the date alone). Offline: the upload queue is in memory, and paused uploads resume on reconnect (PHOTO-09). They aren't kept across reloads in v1.

**As built (B05).**
- The request body is the raw file (`xhr.send(file)`), not multipart: `Content-Type` is the file's type, `Content-Length` its size, and `x-file-name` (`FILE_NAME_HEADER`) its name, URI-encoded. The photo id is a server-made UUIDv7 (`Transport.upload` has no id).
- The server runs the same `uploadProblem` check as the client on the declared type and size before reading the body, then counts bytes while streaming to `{id}.orig` and stops at 20 MB → `too-large`. Bytes `sharp` can't decode, or a format outside D12's list → `not-a-photo`. A refused or failed upload leaves no files and no row.
- `taken_on` = EXIF `DateTimeOriginal` (else `DateTimeDigitized`) as written by the camera, else the upload day in the account's time zone (L03: `accountTimeZone`, §6.4). `created_at` = `updated_at` = server now. The row is stamped with the next version in one transaction and announced on the sync bus, so other displays pull it (§5).
- The file route streams the file with `Cache-Control: private, max-age=31536000, immutable` (photos never change in v1) and `X-Content-Type-Options: nosniff`. Copies are `image/webp`; the original's type comes from its decoded format.

### 6.4 Jobs
`instrumentation.ts` → `register()` runs migrations, then starts timers (B01 runs the migrations through `server/boot.ts`; B07 adds the timers). **Note expiry** runs hourly and soft-deletes notes older than the account's `noteExpiry`. **Link cleanup** runs daily. Backups belong to the PostgreSQL host (P02 removed the SQLite `VACUUM INTO` job).

**As built (B07).**
- `bootServer()` calls `startJobs()` after the migrations. One timer ticks every hour (`unref`, so it never keeps the process alive), plus a first tick at boot. `createJobTick` runs the hourly jobs on every tick and the daily jobs on the first tick of each UTC day, so a restart catches up at once. Jobs are `async` (P02): the tick awaits each in turn, and a job that throws or rejects is logged and doesn't stop the others or later ticks.
- **Note expiry** (`expireNotes`, hourly) uses the screens' `noteExpired` rule from `domain/notes.ts` (age since `createdAt` past 24 h or 7 days; `null` never; no settings row = the default week). The time zone doesn't change an elapsed-time rule, so it isn't read (spec v0.30). In one transaction each expired note becomes a tombstone like a `DELETE` (§6.1: `deleted_at` = `updated_at` = now, next version, content kept). The job answers each account's newest version, and `startJobs` publishes it on the sync bus, so open displays pull the tombstones (§5). It runs across accounts (CLAUDE.md exception) but reads each account's own setting for that account's notes only.
- **Account time zone (L03, spec LOC-07).** `services/rows.ts` `accountTimeZone(db, accountId)` = the settings row's `weatherLocation.timeZone`, else `accounts.time_zone`, read in one query (`coalesce(settings.json -> 'weatherLocation' ->> 'timeZone', accounts.time_zone)` over `accounts LEFT JOIN settings`, scoped by the account id; P02). `uploadDay` (photos) is its only reader today. The zone is stored once, with the place, so nothing has to copy it to `accounts` when the location changes.
- **Link cleanup** (`cleanupLinks`, daily) deletes `magic_links` rows whose `expires_at` is more than 24 h ago, used or not. Younger ones stay so `/api/auth/status` can still answer `expired{email}` or `finishing-elsewhere` for them (§6.2).

### 6.5 Config
`server/env.ts` parses `process.env` with Valibot at boot: `DATABASE_URL` (a `postgres://` or `postgresql://` URL, P02), `DATA_DIR` (photos), `APP_URL`, `RESEND_API_KEY`, `MAIL_FROM` (`APP_URL` must be a URL, the others non-blank). Bad config fails fast: the error names the bad variables without their values (`RESEND_API_KEY` is a secret), and `bootServer()` exits the process, since Next would otherwise keep serving 500s. `next build` doesn't run `register()`, so CI builds need no env. `.env.development` (committed, dev server only) sets `DATABASE_URL=postgres://localhost:5432/glance` (a local PostgreSQL with a `glance` database, see the README; the dev server stops at boot without it) and points `DATA_DIR` at `.data/` (git-ignored); it holds no API key: each developer puts their own `RESEND_API_KEY` in `.env.development.local` (git-ignored), and the dev server stops at boot without one. `server-only` (pinned 0.0.1) marks every `src/server` module; Vitest aliases it to its empty file. Tokens are random and stored as sha256 hashes, so no signing secret is needed.

`NEXT_PUBLIC_DEMO=1` makes a **demo build**: fixture URL params, `/dev/gallery` and "Continue as guests" (SIGNIN-05; removed in handoff v5, U15) are compiled in. Demo uses the `glance-fixture` DB with `FixtureTransport` and skips the `glance-meta` gate. `next dev` implies it. Production builds leave it unset. Demo-only routes are named `page.demo.tsx`: `next.config.ts` adds `demo.tsx` to `pageExtensions` only for the dev server (`PHASE_DEVELOPMENT_SERVER`) or `NEXT_PUBLIC_DEMO=1`, so a production build never compiles them (its route list has no `/dev/gallery`).

## 9. Spec changes from this design

Confirmed 2026-10-11 and applied to the product spec (v0.5):

1. **D9 / D10** refine SYNC-02/03: SSE becomes a "changed" ping plus a versioned pull, and the server's arrival order decides last write wins (not the client's `updated_at`).
2. **D8** client UUIDv7 IDs. **D12** `sharp` copies. **D15** no date library. **D11** 2 s polling for the waiting screen.
3. Offline photo uploads aren't kept across a reload (§6.3).
4. Schema changes to the spec's §7.0: add an `accounts.time_zone` column, a `version` column on synced tables, and a `sync_state(version)` counter table.

Applied in spec v0.6 (offline cold start, §4.5):

5. §3 Offline bullet: installable PWA that cold-starts offline, HTTPS required, home-screen install recommended on iPad kiosks.
6. §8.1 **SIGNIN-13** (new): if the server no longer accepts the screen's session, it returns to the sign-in form. Unsynced changes are kept and sent if the same account signs in again.
7. §8.5 **NOTE-08**: expired notes are hidden on the screen too, even offline.
8. §9.5 **OFF-06** (new): cold start offline with every view and photos available. **OFF-07** (new): updates apply only while the screen is idle with nothing waiting to sync.

Applied in spec v0.7 (no e2e tests, D18):

9. §11 Phase 2 exit criteria: dropped "optionally Playwright visual snapshots". Screenshot review stays.

Applied in spec v0.8 (design review):
