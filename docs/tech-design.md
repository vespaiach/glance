## 1. Decisions

| # | Area | Decision |
|---|---|---|
| D1 | Framework | **Next.js App Router, run as a SPA.** A persistent client shell in `(display)/layout.tsx` keeps the clock, idle, slideshow and sync timers alive across views. Views are `'use client'` segments. |
| D2 | Language / lint | TypeScript `strict`, Biome (lint + format, pre-commit and the §7 checks). |
| D3 | Styling | **StyleX** via Babel + PostCSS (`useCSSLayers: true`); `globals.css` holds only `@stylex;`. Tokens in `theme/` (`tokens.stylex.ts`, `type.stylex.ts`, `seasons.stylex.ts`), seasons and Ambient as `createTheme` in `themes.ts`. Components use `season.*` roles directly. Geist / Geist Mono are vendored woff2 loaded with `next/font/local`. `ui/Icon` wraps `lucide-react` and takes the glyph component, not a name. |
| D4 | Client data | **Local-first store on IndexedDB (Dexie).** The UI reads local data only; writes go local first; a sync engine in a Web Worker (D19) talks to the server. |
| D5 | Shell state | React context + `useSyncExternalStore` stores. No state library. |
| D6 | Validation | **Valibot** schemas in `domain/schemas.ts` are the single contract for client and server; types come from `v.InferOutput`. `SyncedXSchema` adds `updatedAt`, `version`, optional `deletedAt`. IDs are UUIDs, timestamps ISO-8601, dates `YYYY-MM-DD`. Schemas never transform. The event schema checks `endAt > startAt` and a span under 24 h. Weather icons are a closed set of Lucide kebab names that `ui` maps to components. `DEFAULT_SETTINGS` in `domain/defaults.ts`. |
| D7 | Database | **A `Database` port** (`server/db/database.ts`): one repo per table with methods shaped like the domain (`events.find/save/changedSince`, `tags.liveByName`, `versions.next`, …) plus `tx(fn)`. A transaction is atomic and runs **one at a time** against other transactions; a nested `tx` joins the outer one; inside `fn` only the handle it gets is used. Services, auth and jobs import only `server/db` (Biome blocks the adapters), get the `Database` in their deps and keep every rule themselves (ownership, tombstones, stamping, name checks). Adapters, picked by `DB` (§6.5): **`postgres`** (default), `pg` with raw SQL in `server/db/postgres/*`, whose `tx` takes the `sync_state` row lock first (also for `memory`); `timestamptz` → ISO string, `bigint` → number, `date` stays `YYYY-MM-DD`; migrations are `db-migrations/NNN_*.sql`, applied at boot by `prepareDatabase()` (one transaction each, tracked in `schema_migrations`); tests run it on **PGlite**. **`memory`** runs the same adapter and migrations on an in-process PGlite (`openPgliteDatabase`), which runs one query or transaction at a time; nothing survives a restart (dev). The adapter passes `databaseContract` (`server/db/contract.ts`); another store (a file, Google Sheets) is one more adapter that passes it. |
| D8 | IDs | **UUIDv7 generated on the client** (`domain/id.ts`). Offline creates need no remapping. Server-made ids (accounts, displays, photos) are UUIDv7 too. |
| D9 | Sync | Outbox push + versioned pull. SSE only says "something changed"; 30 s polling is the fallback (§5). |
| D10 | Conflicts | Last write **to reach the server** wins. The server stamps `updated_at` and `version`. |
| D11 | Auth | **Emailed 6-digit code** typed on the screen that asked for it (QR links stay, D23); opaque session token in an httpOnly cookie. A code is `crypto.randomInt(0, 1_000_000)` zero-padded; only `sha256(email + ":" + code)` is stored, one live row per email in `sign_in_codes` (a new send replaces it), 10 min life, 5 tries, then the row is dead. `verifyCode` runs in one transaction (D7), checks expiry first (an expired or missing row is `code-expired`, even when locked), then the try count, then compares the hashes with `timingSafeEqual`; a wrong try bumps `tries` in the same transaction. Codes come from `AuthDeps.newCode`, so tests pass fixed ones. Session tokens and QR tokens are 32 random bytes (base64url); only their sha256 is stored. No polling and no `pending` or `link_email` cookies: the verify answer signs the screen in. Migration `008_sign_in_codes.sql` creates `sign_in_codes`, deletes the email rows of `magic_links` and drops its `kind`, `email`, `time_zone` and `pending_id` columns (and the shape check), making `account_id` and `display_id` required. Cookie: `session` (400 days, `HttpOnly; SameSite=Lax; Path=/`, `Secure` on https), renewed for another 400 days by every `GET /api/sync` (`renewSession`), so a screen in use never signs itself out (§6.2). |
| D12 | Photos | Two objects per photo, keyed `{account}/{id}.{display|thumb}` (`photos.file_path` holds `{account}/{id}`; `photos.files_removed` marks a tombstone whose objects are gone, migration `012_photo_files_removed.sql`), in a **`PhotoStore`**: local disk, AWS S3 or Cloudflare R2, picked by `PHOTO_STORE` (§6.3, §6.5). **`sharp`** makes WebP display (≤ 2560 px) and thumb (≤ 640 px) copies, upright by EXIF; the original is read for details (D22) and decoded, then discarded, never stored. Delete and the daily job also remove `{file_path}.orig`, and `removePhotoOriginals` (run once at each server start, idempotent) removes the `.orig` object of every live photo, so originals stored before this cleans up. Raster formats `sharp` decodes are accepted; SVG is refused. |
| D13 | Weather and places | **Open-Meteo** forecast + geocoding behind `WeatherProvider`; **US Census Geocoder** behind `PlaceLocator` for reverse lookup. Both via `getJson` (8 s timeout, Valibot parse, any failure → `weather-failed`). Forecast cached per account for 15 min (`weather_cache`). Place search is US only, keeps names matching the query (a ZIP keeps all), requires a valid IANA zone, at most 5. `locatePlace` rounds to 2 decimals and asks the Census place and the Open-Meteo zone in parallel. |
| D14 | Email | A **`Mailer`** (`send` answers `Result<void, "mail-failed">`) with one adapter per provider, picked by `MAIL_PROVIDER`: **Resend**, **Mailtrap** and **Mailgun** over their HTTP APIs with plain `fetch`, **SMTP** with **`nodemailer`**, and **Mailpit** (the SMTP adapter on a local catch-all, the dev default). Every provider sends from `MAIL_FROM`. One attempt, no retry or fallback provider (§6.2, §6.5). |
| D15 | Time | No date library: `Intl.DateTimeFormat` + pure helpers in `domain/time.ts`, `week.ts` and `zone.ts`. "Local" means the **screen's time zone** `tz` (the saved place's zone, else the device's), never the device's: every helper that reads hours or dates takes `tz` last. `zone.ts` converts wall time ↔ instant (`wallTime`, `zonedInstant`, DST-safe: a skipped time moves forward, a repeated one is the earlier instant) and days (`dayNumber`, `dateKey`, `dayStart`, `addDays`). A date with no time (day key, `takenOn`, forecast day, month cell) is a UTC-midnight `Date` formatted in UTC. Formatters take minutes of the local day. `localZoneGuard.test.ts` bans local-zone `Date` getters in `src`; Vitest pins `TZ=Asia/Kolkata`. |
| D16 | Offline shell | **Serwist** PWA: precache build assets, fonts and public files; cache route HTML on activate and RSC payloads as fetched; NetworkFirst (3 s) for navigations and RSC; CacheFirst for photo files with warming; NetworkOnly for other `/api/*`. New versions activate only when idle (§4.5). |
| D17 | Runtime | **One Node process** (`next start`) behind HTTPS, with the database picked by `DB` (PostgreSQL at `DATABASE_URL` by default) and photos in a persistent `DATA_DIR` (`disk`) or an S3 or R2 bucket. Migrations run at boot. One process is required by the in-process SSE bus and the `memory` database. |
| D18 | Tooling | npm with exact pins (except `web-push` and `@types/web-push`, on `^3.6`), Node 24 (`.nvmrc`). Vitest + Testing Library + `fake-indexeddb`; Vitest compiles StyleX through `@rolldown/plugin-babel`. **No e2e tests** (§7). `comlink` for worker messaging, `dexie-react-hooks` for `useLiveQuery`, `exif-reader` for photo details (D22). |
| D19 | Sync host | Sync runs in a **dedicated Web Worker** per tab. The page keeps reads and repo writes; the worker does push, pull/apply, SSE, polling, retries and weather (§4.6). |
| D20 | Location | The browser position (`devicePosition`: low accuracy, 10 s timeout, `maximumAge` 10 min) goes to the server, which turns it into a place with its zone (D13). Offered only with `geolocation`, a secure context and permission not `denied`. Failures: `denied`, `no-position`, `outside` (404), `lookup` (5 s limit, 5xx, network). The browser never calls a geocoder. |
| D21 | All-day events | `allDay: true`, `startAt` = the date's **UTC midnight**, no `endAt`, so the date never moves with the zone or DST. Repos read a day as timed events in `[dayStart(key, tz), dayStart(key+1, tz))` plus all-day events at that UTC midnight. `eventDayKey(event, tz)` is the one place that reads an event's date. Server: `events.all_day` with `CHECK (NOT all_day OR end_at IS NULL)`. |
| D22 | Photo details | Read on upload, **on the server**: title (`ImageDescription`/`XPTitle`), date (`DateTimeOriginal`/`DateTimeDigitized`), GPS → `placeAt` → "City, ST". Fallbacks from pure `domain/photoName.ts` (`nameFromFile`, `dateFromFile`), then `x-file-modified`, then the upload day. Rows store `sources` and `checked`. Photos are editable (`PUT` title, date, place, sources, checked) and deletable (tombstone; files removed after commit). |
| D23 | Screens and QR | `GET /api/displays` lists the account's displays (`kind`, `browser`, `lastSeenAt`, `current`); a transport read, not synced. Kind and browser come from the `User-Agent` (`domain/screens.ts` `deviceOf`); the name is built from them, not stored. QR sign-in is the only user of `magic_links` (account + display ids, 3 min expiry) and `GET /api/auth/verify`; the code is drawn on the client with `uqr`. |
| D24 | Tags | **`tags` is a synced entity** like notes (`PUT` and `DELETE /api/tags/{id}`; tags are never renamed or recolored, so a `PUT` of an existing id with another name or color is refused, 409 `tag-changed`; the same `PUT` again answers the stored row and bumps nothing). Pulled by `/api/sync` as entity `tags`. **Removing a tag** (FAM-08): `DELETE /api/tags/{id}` soft-deletes it and, in the same `tx`, soft-deletes the account's live events whose only tag it is and drops it from the other events' `tag_ids`, one version bump per changed row; everyone events don't change. Removing the account's last live tag → 409 `last-tag` (the screen hides Remove for the last member too); another account's or an unknown id → 404; removing a removed tag again answers its tombstone and bumps nothing. The service is `removeTag(accountId, id)` (`Result<SyncedTag, "not-found" | "last-tag">`; the events are stamped before the tag, so the tag carries the highest version and is what the sync bus announces), using `events.liveWithTag(accountId, tagId)` and `tags.liveCount(accountId)`. The engine pushes the tag `delete` like any other; a 409 is `invalid`, so the entry is dropped and the next pull from scratch restores the server's rows. The new endpoint raises `CLIENT_BUILD`; `MIN_CLIENT_BUILD` stays, since no row changes shape. `TagsRepo.remove(id)` applies the same rule locally in the same Dexie transaction as the tag's `deletedAt` and queues one outbox entry, a tag `delete`, with no per-event entries; the next pull overwrites those rows with the server's. The unique name index covers live tags only, so a removed name can be added again as a new tag. Events store **`everyone boolean`** plus **`tag_ids text[]`** (empty when `everyone`; empty and not `everyone` = nobody), not a join table, so an event stays one row on the wire and in the outbox; a tag added later joins every `everyone` event with no rewrite. Tag colors are a closed set of 12 names mapped to the design system's `--block-*` colors in `theme`, never season roles. The server keeps `tag_ids` honest: an event `PUT` drops ids that aren't live tags of the account (so another account's ids never stick); an event left with none is stored as nobody. A tag `PUT` with a new id and a name a live tag of the account already has (ignoring case) answers that live tag and bumps nothing; a partial unique index on `(account_id, lower(name))` backs it. When a push answer's tag id differs from the pushed one (two screens added the same name offline), the engine deletes the local tag and moves its id to the answered one in the screen's events and their outbox payloads, in the same transaction. The first tag is created with the name (`POST /api/auth/name`), with a UUIDv7 id and the first color. Migration `009_tags.sql` renames `members` → `tags` and `events.member_ids` → `tag_ids` (indexes and constraints too), drops tombstoned tag rows, and bumps one version per account so screens pull the new entity; the shape change raises `CLIENT_BUILD` and `MIN_CLIENT_BUILD` (§4.5). Pure rules (`domain/tags.ts`): `whoLabel`, `eventColor`, `nextFreeColor` (the New member tile's preselected swatch: first unused, else the first), `matchesFilter(event, selected, allIds)` (CAL-05: tags in common; everyone events while any tag is selected; nobody events only when every tag is), `toggleFilter` (adds or removes one id; a filter left with every tag becomes `"all"`), `toggleEveryone` (the Everyone row: `"all"`, or nobody when every tag is selected), `filterLabel(selected, tags, labels)` (Everyone / the names for 1–2 in tag order / "{n} people" / "No one"), `filterScope` (`everyone | some | none`, the free-slot label), `initials(name)` (CAL-05: up to 3 letters in full, else the first letters of the first two words split on spaces and hyphens, upper-cased, else the first two letters), `stackCircles(shown, max)` (up to `max` circles, else `max − 1` and a "+N" count), `liveFilter` (the person filter against the live tags → the selected ids: `"all"` selects every tag, new ones included; gone ids drop; a non-empty selection left with no live id selects every tag, CAL-05), `memberRemoval(events, tagId)` (FAM-08: the ids of the live, not-everyone events naming the tag, split into `deleted` (it is their only tag) and `stripped` (shared); past events count), `removalLine(removal, labels)` (FAM-08's result line from `copy.tags.removal`), `filterTagIds` (a new event's people `{ everyone, tagIds }` from the filter in tag order; everyone when all are selected, nobody when none are), `whoValue(ids, allIds)` (a Who draft → `{ everyone, tagIds }`, every tag = everyone, also when there are no tags yet; ids not yet in `allIds`, like a tag just added, stay on), `whoIds(event, allIds)` (an event's people → the Who draft's ids; everyone = every tag), `pickWho(tagIds, allIds, tagId?)` (EVT-11's Who chips: no id = Everyone = every tag; a tag picked while every tag is on keeps only that tag; otherwise it toggles, in tag order, and unpicking the last one gives every tag) and `exactTag(tags, input)` (the tag with that trimmed name, any case). `domain/tagMatch.ts` `suggestTags(tags, input, exclude)` ranks EVT-11's fuzzy matches (prefix → word prefix → contains → subsequence → one edit with 3+ characters against the name's prefix of the input's length or the whole name, on names folded by case, accents (đ → d), spaces and hyphens; ties keep tag order). Events have no color of their own; person dots are `ui/PersonDot` (a tag color or the season soft color). |
| D25 | Day timeline | **Pure layout in `domain/timeline.ts`**: `timelineLayout(plans, { day, now, tz }, { span: "day" \| "24h", height, width, passedFactor, minPlanHeight, minHourHeight, minColumn, longStrips, firstHour?, lastHour?, nowDot? })` with no DOM (`width` is the box minus the hour gutter). `plans` are the day's timed plans, already filtered by the person filter. It returns `rows` (hour weights per TL-02 and TL-06; each row gets `min(minHourHeight, height ÷ rows)` and the rest of the height is shared by weight, TL-01), `marks` (hour lines with label and hairline thinning, TL-01, TL-06), `plans` (top, height with the 48/40 px minimum, `left` / `width` as fractions of the column area per TL-03 and TL-12, `startsBefore` when clipped at 5 AM), `strips` (with `longStrips`, plans over 3 hours as 44 px strips 52 px apart, `stripsWidth` taken off the column area, TL-13), `more` (TL-12: when a cluster has more columns than `width ÷ minColumn`, the columns that fit `(width − 52) ÷ minColumn` stay, the last one runs to the edge when nothing folded overlaps it, and the folded plans group into tiles with `count`, `start`/`end`, `first` (earliest start), `left`, a 48 px minimum height and `tall` from 60 px), `freeSlots` (TL-08, with the New event `start`/`end`; slots whose tile, height − 8 px, is under 44 px are dropped), `now` (TL-09) and `hiddenOutsideSpan` (CAL-06; 0 on 24 hours). A plan with no end takes 30 min on the timeline. Overlaps are found on pixel boxes after the minimum height, so a short plan pushed down by it still gets its own column. `DayTimeline` measures its card with a `ResizeObserver` and passes the height; the card's content tier (TL-04) is picked from its measured size. Calendar and Today pass different options: Calendar large and normal 200 px columns, 26 px hour rows and strips; Calendar small none of them; Today 120 px columns and strips; `passedFactor` 0.35 / 0.3; rain chips on Calendar off phone. Both show gutter weather (TL-07, no lane): `hourWeather(layout, sky, sparse)` picks the hours, every hour with room on Calendar and, with `sparse` on Today, only the first, an icon change, rain (≥ 50%) starting or stopping, else every 3 hours. The now line sits behind the plan cards and cards have no NOW pill or strikethrough (TL-05, TL-09). The "+N MORE" tile calls `onOpenMore(earliestId)`: Calendar opens that plan, Today opens Calendar. The Calendar's 24 hours link count (CAL-06) uses `outsideDay(plans, tz)`. `firstHour` starts a "day" span later than 5 AM and `lastHour` ends it later than 9 PM (Today's Earlier fold; hours past 9 PM weigh as TL-02, free slots stay 5 AM – 9 PM), and `nowDot` lets hour labels sit up to 10 px from the now line instead of 22 (TODAY-11's circle). `grownHeight(plans, context, options)` returns `options.height` scaled (at most 3×) until every plan not yet ended has `92 + 4` px between its start and end on the timeline (`66 + 4` under 30 min). Today's `TodaySchedule` renders the all-day tiles and a `today` timeline through the person filter, or, on a day with no plans, Coming up, or the empty timeline when nothing is ahead (TODAY-06). |
| D26 | Breakpoints | **Three sizes**, `type Breakpoint = "large" \| "normal" \| "small"` in `domain/breakpoint.ts`: `breakpointFor(width)` → small at 768 px and below, normal up to and including 1200, else large (spec §5.1). `useBreakpoint()` reads the window width live (the sidebar doesn't count). Every layout record, component prop and test names these three; normal takes the large record unless the spec names normal (Today, Upload's QR panel). Box-width rules (Today's 450 / 440 / 400 px cards, the week cells' 120 / 56 px, the timeline columns) measure the box with `ui/useBoxSize`, never the window. |
| D27 | Notes | **One paper tone:** `Note` has no `tone` (`NoteSchema`: `text` 1–280 characters after trim, `author` 0–32, blank = unsigned, `createdAt`, `rotation`). Migration `011_note_tone.sql` drops `notes.tone`; Valibot's `object` drops the `tone` an older client still sends, so the server ignores it. The Dexie v5 upgrade deletes `tone` from stored notes and waiting note puts. The limits are `NOTE_LIMITS` in `domain/schemas.ts`, also the fields' `maxLength`. The client build goes up with the shape (`CLIENT_BUILD`); `MIN_CLIENT_BUILD` stays, since older clients' notes still validate. The paper is the season's `soft` role. The board's 120-character cut (`domain/notes.boardText`, at a word, "…") is derived, never stored. The last author posted from this screen is `meta.lastAuthor` in the account's Dexie database (per screen, never in the outbox, gone with the database at sign-out): `NotesRepo.post` (New note) sets it when the author isn't blank, `put` (Edit) leaves it, and `useLastAuthor()` reads it ("" before the first post). |
| D28 | Ambient brightness | `AccountSettings.ambientBrightness: "full" \| "medium" \| "low"` is `v.optional(…, "medium")` in the settings schema, so stored settings without it read as Medium with no data migration. The ink is a color token per level (`colors.white`, `ambientInkMedium` `#dcdcdc`, `ambientInkLow` `#a3a3a3`) that `AmbientView` sets as the root `color` (icons use `currentColor`), checked at 4.5:1 on every deep color in `theme/contrast.test.ts`. Browsers can't set the backlight, so the ink is the whole effect. The burn-in drift (AMB-11) is a pure `driftOffset(step)` over 8 fixed offsets (each axis within ±6 px, the prototype's list), the step `driftStep(now)` = whole 2-min periods mod 8, never a timer; the four rows take it as a `translate` with a 2 s transition (0 s under reduced motion), which composes with the AMB-10 row `transform`s. The top row's single status is `ambientStatus({ signedOut, offline })` (signed out wins). The hint fades with a CSS animation (1.2 s after a 10 s delay), so it needs no timer either. |
| D29 | Reminders | `CalendarEvent.notify` (`v.optional(v.boolean())`; missing = on) is the event's Notification (NOTIF-09); settings carry `notifyLead` (`v.optional(v.picklist(["off", 15, 30]), 15)`, one lead time per account, NOTIF-08) and `chime` (`v.optional(v.boolean(), true)`). Migration `017_notify.sql` replaces `events.reminder` with `notify boolean NOT NULL DEFAULT true` (`reminder = 'off'` → `false`, else `true`) and rewrites each settings row's `defaultReminder` as `notifyLead` (`off` → `"off"`, else 15) with one new version per account, and deletes the at-start `reminder_sends` rows so their `kind` check becomes `15min` / `30min`; the Dexie v7 upgrade does the same to stored events and settings and to waiting event and settings puts; `CLIENT_BUILD` and `MIN_CLIENT_BUILD` go up (§4.5). The event page's draft carries `notify` (`true` for a new event). Nothing about a reminder is stored on the client: `domain/reminders.ts` `remindersDue(events, lead, now, seen)` derives the reminders due at `now`: none when `lead` is `off`, else one fire at start − lead for each timed event whose `notify` isn't `false` (a fire due within the last minute, or missed but before the start, NOTIF-02); it groups fires of the same minute (`ReminderGroup`: `fireAt`, `startAt`, `events` in start order, their `keys`, `titles` = all up to 3, else 2 and `more`) and drops keys in `seen` (`{eventId}:{fireAt ms}`, so a moved event or a changed lead fires again); `minutesLeft(group, now)` gives the real time left for the eyebrow. There is no fire at the start. `ui/ReminderStrip` takes plain strings (`eyebrow`, `title`, `label`, `actionLabel`, built from `copy.reminder.strip`), the dot color and `left` (the time-left fraction, so the host drives the bar from `now`); it is a `status` region whose Details button has `tabIndex -1` and whose `mousedown` is prevented, so neither showing nor tapping it moves focus. The shell's `ReminderHost` (in `DisplayProviders`, inside `IdleProvider`) reads today's and tomorrow's events (`useEventsBetween`) and `useNow("second")`, keeps `seen` and the showing group (with the time it showed) as tab state, shows the latest due group and marks every due group seen, and renders `ui/ReminderStrip` in a fixed top layer (z 30, above sheets and the drawer) that is not part of the focus order; a window capture listener stops `pointerdown` and `wheel` inside it, so the idle and sidebar activity listeners and outside-tap handlers never see them. It closes 30 s after it shows (derived from `now`, not a timer of its own; the 280 ms slide-in and the fade before the close are CSS animations keyed to the showing group). A tap closes it and opens Event details (`SheetHost`), or Today for a group. In ambient hours (`inAmbient`) it shows nothing and due groups are only marked seen; `AmbientScreen` derives its Next slot with `ambientReminder(events, lead, now, tz)` (none when `lead` is `off`; timed events with `notify` on whose fire has passed and that haven't ended, or whose day hasn't ended when there is no end; the latest start wins). The chime is two short Web Audio sine notes (`shell/chime.ts`, no audio file); the `AudioContext` is created on the first `pointerdown`, so a screen nobody has touched since loading stays silent. |
| D30 | Web push | **`web-push`** on the server with VAPID keys from `server/env.ts` (§6.5; push is off when they are unset, and `GET /api/push/key` answers 404). `push_subscriptions` (migration `014_push.sql`, with `reminder_sends`) holds one row per browser subscription, keyed by `endpoint`, scoped by account and display, and goes with its display (`ON DELETE CASCADE`, so sign-out drops it); `PUT /api/push/subscription { endpoint, keys }` (`PushSubscriptionSchema`: an `https:` endpoint) upserts it for this display, replacing the display's other subscription (an endpoint seen before moves to this account and display, since only that browser knows it), and `DELETE` removes this display's. The **reminder job** (`server/jobs/reminders.ts`, every minute, §6.4) reads the live one-off events starting 14–15 or 29–30 minutes ahead (`events.liveStarting`) and every live weekly series (`events.liveWeekly`), across accounts, expands them per account to the occurrences of today and tomorrow in `accountTimeZone` (`occurrencesBetween`, D38) and keeps those starting in the lead's window, so only fires from the last minute are due, applies the same `remindersDue` rule per account with its `notifyLead` to the events in that lead's window only (`seen` = nothing; an account whose lead is Off gets nothing), inserts each fire into `reminder_sends` (`kind` = the lead, `15min` or `30min`; `ON CONFLICT DO NOTHING … RETURNING`, primary key `(event_id, kind, fire_at)`), runs `remindersDue` again with the fires already sent as `seen` and sends one push per remaining group to each of the account's subscriptions, with the NOTIF-07 title and body (times in `accountTimeZone`) and `data.url` (`/today?event={id}`, which opens Event details over Today, or `/today?at={HH:MM}` for a group). The push client is `server/push` `createWebPush(config)` → `PushSender` (`Result<void, gone | failed>`, TTL 15 min), faked in tests; the job runs only when the VAPID keys are set. A 404 or 410 from the push service deletes that subscription; other failures are logged and not retried. Missed pushes (server down) are not sent late: only fires from the last minute count. The service worker's `push` handler (`data/sw/push.ts` `showPush`) skips `showNotification` when a Glance window is `visible` (`clients.matchAll`) and drops a payload whose `data.url` isn't a same-origin path; `notificationclick` (`openPush`) focuses the first Glance window and navigates it to `data.url`, or opens a window there (`/today` for a bad url). `TodayScreen` follows `?event={id}` by opening Event details, and both `?event` and `?at` are then replaced by `/today`; `?at` adds nothing to Today, which already lists the group's events. ## 4. Client design

### 4.1 Local store (Dexie)
```ts
db.version(8).stores({
  events:   'id, startAt, deletedAt, repeat',   // + everyone, tagIds, notes, notify
  tags:     'id, createdAt, deletedAt',
  members:  null,
  notes:    'id, createdAt, deletedAt',
  photos:   'id, createdAt',
  settings: 'accountId',
  weather:  'accountId',
  outbox:   '++seq, entity, entityId',    // { seq, entity, entityId, op: 'put'|'delete', payload?, attempts }
  meta:     'key',                        // cursor, status, lastAuthor
});
```
- The v3 upgrade copies `members` into `tags` (live rows) and renames each event's `memberIds` to `tagIds`, also in waiting outbox payloads; waiting member puts become tag puts and member deletes are dropped; the v4 upgrade rewrites the stored settings, and any waiting settings put, as `010_settings_values.sql` does; the v5 upgrade deletes `tone` from stored notes and waiting note puts, as `011_note_tone.sql` does (D27); the v6 upgrade sets `reminder: "15min"` on stored events and waiting event puts without one, as `013_event_reminder.sql` did; the v7 upgrade replaces each event's `reminder` with `notify` (`off` → `false`, else `true`) and the settings' `defaultReminder` with `notifyLead` (`off` → `"off"`, else 15), in stored rows and waiting puts, as `017_notify.sql` does (D29); v8 only adds the `repeat` index (D38). The server migrations do the same, so both sides agree before the first pull.
- **One database per account** (`glance-{accountId}`), deleted on sign-out.
- Rows keep the server's soft delete (`deletedAt`); hooks filter it out.
- Pending ("Waiting to post") is derived from the outbox, never stored.
- Wire format = domain types (camelCase). Snake_case exists only in SQL.
- Range queries compare ISO strings; every stored timestamp is UTC `toISOString()`.

### 4.2 Repository pattern
Each repo has a small interface and one Dexie implementation (`createXRepo(store)` + a `useXRepo()` hook). A write is **one Dexie transaction** — the row plus an outbox entry — then `nudge()` once it commits. A put keeps the stored server fields (a new row gets version 0); a remove sets `deletedAt` locally and queues a delete. Settings are one row keyed by `accountId`, merged over defaults. Photo uploads skip the outbox (§6.3); photo edits and deletes use it.

Hooks are `useLiveQuery` reads (`undefined` while loading, deleted rows filtered): events by day, week or span (`useEventsOnDay`, `useEventsInWeek`, `useEventsBetween`) in `tz`, with every weekly occurrence in the span (D38), all-day first, then by start, `useEvent` (the stored row, so a series opens as itself), `useNextEventAfter` (a series counts at its next occurrence), `useEventsAfter(day, tz)` (every all-day and timed event after the day, and each series once at its next occurrence), `useUpcomingEvent`, `useHasEvents`, `useLiveEvents` (every live event, past ones too; the Settings member counts, FAM-08), `useEventRecents` (`recentTitles` / `recentPlaces` of the live events, EVT-12), `useTags` (oldest first), `useNote`, `useNotes(now)` (newest first, expired hidden, `waiting` derived), `usePhotos`, `usePhoto`, `usePhotoSrc`, `useTodaysPhoto(day, tz, skip)`, `useSettings`, `useWeather`, `useSyncStatus`, `useSourceStatus`, `useRetry`, `useSignedOut`, `useOutboxEmpty`. So every view updates by itself after any write (EVT-07, FAM-05). `TagsRepo.add(tag)` and `TagsRepo.remove(id)` (D24) are the tag writes; Settings builds the FAM-08 rows with `features/settings/members.ts` (`memberRemoval` + `removalLine` per tag) for the pure `MemberList`, and keeps which row asks in local state; `outbox.ts` `queued(store, tables, write)` runs several row writes and their outbox entries together.

`RepoProvider` takes a `RepoStore` (`db`, `accountId`, `account`, `now`, `startedAt`, `nudge`, `refreshWeather`, `photoSrc`, `upload`, `places`, `locate`, `displays`, `photoUsage`, `issueQr`/`voidQr`, `webPush`, `imports`, `signOut`, `signOutAll`, `deleteAccount`, `markSignedOut`, `markRevoked`). The shell builds it; tests inject one.

**Transport.** Every server call is a `Transport` method returning `Promise<Result<T, TransportError>>`, with `TransportError` = `network` · `unauthorized` (401) · `revoked` (401 `revoked`, D31) · `invalid` (any other non-2xx: 400, 404, 409, …) · `outdated` (426) · `server` (5xx, 429, 403, non-JSON 2xx). Methods: `push(entry)` → `Change`, `pull(cursor?)` → `{ cursor, changes }`, `weather`, `places(query)`, `locate(coords)` (adds `outside`), `upload(file, modifiedOn, onProgress)` (adds `too-large` / `not-a-photo` / `storage-full`), `displays`, `photoUsage` (D32), `issueQr`/`voidQr`, `webPush.*` (`key`, `subscribe`, `unsubscribe`; D30; `push` is the outbox write), `apiKey.*` (`get()` answers `undefined` on 404, `create()`, `revoke()`; D40), `imports.*` (`upload(file, forDisplay?)` adds `not-ics` / `no-upcoming` / `too-large`; `staged()` answers `undefined` on 404; `commit(id, who)`, `last()` (`undefined` on 404), `undo(id)`; D39), and `auth.*` (`sendCode`, `verifyCode`, `verifyLink` (D33), `status`, `name`, `location`, `signout`, `signoutAll`, `deleteAccount` (D31)). Callers drop stale answers rather than cancel.
- `HttpTransport` talks to the same-origin API with fetch (XHR for upload progress) and sends `X-Glance-Build: {CLIENT_BUILD}` on every request. Bodies are trusted as typed.

### 4.5 Offline boot and caching
A signed-in screen must cold-start offline with every view working.

- **Static routes.** Every view, `/ambient` and `/signin` is fully static (no `cookies()`/`headers()`); auth gating is on the client; `useSearchParams` sits in `Suspense`. `/` → `/today` is a `redirects()` entry.
- **Auth offline.** `glance-meta` holds `{ accountId, name, email, signedOut?, revoked? }`, written after sign-in. Offline, trust it; online, a 401 means signed out. Signing in to a different account first deletes the old account's DB and `photos` cache.
- **Photos offline.** After each pull, and at start for every saved photo, the worker sends `photosChanged(ids)`; the page forwards them to the SW, which fetches `thumb` and `display` into the `photos` cache one at a time.
- **Storage.** `navigator.storage.persist()` after sign-in. Manifest: `display: fullscreen`, `start_url /today`, `theme_color #000000`, `background_color #c8e6cd` (the icon's mint), the handoff's PWA icons (`pwa-icons/` copied to the `public/` root: 192 and 512, maskable 192 and 512); the root layout links favicons 16/32/48, apple-touch 180 and the `theme-color` meta. Home-screen install on iPad avoids Safari's 7-day cap.
- **Updates.** A new SW waits. At an idle move with an empty outbox, `IdleProvider` posts `SKIP_WAITING` and loads the target path on `controllerchange`; the SW is checked hourly. **Build check:** every route behind `syncReader` or `syncWriter` (`/api/sync`, entity writes, weather, displays, photo usage, push, QR, location) answers **426** when `X-Glance-Build` is missing or below `MIN_CLIENT_BUILD`. After a 426 the outbox can't drain, so the update applies at the next idle even with entries pending; they survive the reload and the new build pushes them. Without a waiting SW, an `outdated` screen does a full page load at idle instead. **Daily reload:** `IdleProvider` notes when the page loaded; an idle move 24 h or more later (`reloadDue`, `domain/idle.ts`) loads the target path in full (FAIL-05). Any change that adds a field to a synced row raises `CLIENT_BUILD` (`domain/build.ts`) and `MIN_CLIENT_BUILD` (`server/http.ts`), because Valibot drops unknown keys and an older client would write the row back without it. New settings fields use `v.optional(…, default)`, so older rows parse.
- **Sign-out.** Stop the host (terminates the worker), call `auth.signout()` (answer ignored; skipped after `revoked`), clear `glance-meta`, delete the account DB and the `photos` cache, and unsubscribe this browser's push subscription. Sign out all devices calls `auth.signoutAll()` first and stays in the dialog on a failure; Delete account calls `deleteAccount()` the same way (D31).

| Request | Strategy |
|---|---|
| `/_next/static/*`, fonts, icons, manifest, `public/**` | Precache; other `/_next/static/*` CacheFirst `assets` |
| Route HTML | Cached on SW activate (`OFFLINE_PAGES`) + NetworkFirst 3 s → cache → `/today` |
| RSC (`RSC: 1`) | NetworkFirst 3 s, cached by path + segment header, `_rsc` ignored |
| `/api/photos/{id}/file` | CacheFirst `photos` + warming, 300 entries |
| Other `/api/*` | NetworkOnly |

Not used: Background Sync (no Safari/Firefox support, duplicates the outbox), caching API JSON, periodic sync.

**Constraints**
- `@serwist/turbopack` compiles `sw.ts` with esbuild to an IIFE at `/serwist/sw.js`, registered as a classic script by the page itself (not `SerwistProvider`). Turbopack is used for dev and build.
- A plugin rebuilds cached responses (`new Response(body, cached)`) so the Turbopack sync-worker script keeps its `#params` URL.
- The SW is off in `next dev`; test on `next build && next start` over HTTPS.
- RSC caching depends on Next internals: pin Next exactly and rerun the offline manual check (§7) on every upgrade.
- "Offline" means our server is unreachable. A failing weather provider is FAIL-*, not offline.

### 4.6 Sync worker
The worker owns the outbox drain, pull + apply, the SSE stream with 30 s polling fallback, retries, the `glance-sync` lock and weather. Both contexts open the same Dexie DB; Dexie broadcasts changes, so page hooks update by themselves. Status lives in `meta.status`, so every tab reads the same one.

| Direction | Message |
|---|---|
| page → worker | `start(accountId, page)`, `nudge()`, `resync()`, `refreshWeather()`, `ping()`, `stop()` |
| worker → page | `photosChanged(ids)`, `restart()` |
| worker → `meta.status` | `{ online, lastSyncedAt?, error?: 'unauthorized' \| 'revoked' \| 'server' \| 'outdated', retryAt?, weather: idle \| loading{since} \| failed{retryAt} }` |

**Code.** `engine.ts` holds all logic with no Worker/DOM APIs and runs anywhere; `worker.ts` adds the lock, SSE, polling and outbox watch with injectable deps; `sync.worker.ts` only exposes it with Comlink; `host.ts` spawns it.

**Rules**
- **Serial runs.** `nudge()` = drain the outbox (re-read by `seq` before each push, no in-memory copy), then pull. One queue, so an entry is never pushed twice.
- **Pending rows win.** Push answers and pulled rows are written only when no outbox entry remains for that row.
- **Errors** follow §5. `unauthorized` / `revoked` / `outdated` halt the engine and keep the outbox. `network` / `server` keep the entry, bump `attempts`, and retry on the FAIL-03 schedule (`retryDelayMs`: 1, 2, 5, then every 5 min).
- **One active worker per browser:** only the `glance-sync` lock holder syncs. It nudges on a new outbox entry from any tab, on each SSE ping and stream reopen, on `online`, and every 30 s while the stream is closed and no retry is waiting.
- **Weather** refreshes at start, every 15 min, on `refreshWeather()`, and right after a sync that brings a new location (once its settings push is accepted). Failures retry on the FAIL-03 schedule.
- **Timeouts.** Every transport request aborts after 60 s (`REQUEST_TIMEOUT_MS`) and fails as `network`, so a hung request can't hold the queue.
- **Watchdog.** The host calls `ping()` every 60 s; one unanswered within 10 s means the worker died or froze, so the host terminates and respawns it on the same account.
- **Schema upgrades:** on `versionchange` the worker stops and posts `restart`; the page respawns it after its own upgrade. The worker never blocks an upgrade.
- The worker never touches `navigator.serviceWorker`; the page forwards photo ids.

## 5. Sync protocol

**Push.** The engine drains the outbox in `seq` order, one request at a time: `PUT /api/{entity}/{id}` (full row, idempotent upsert) or `DELETE /api/{entity}/{id}`. On 2xx it removes the entry and saves the returned row only if no other entry for that row remains. Errors:
- **401** → keep the outbox, stop syncing, sign the screen out (§4.3). **401 `revoked`** → stop syncing, then the full sign-out deletes the outbox with the account DB (D31).
- **Any other 4xx** (400, 404, 409, 413, 415) → drop the entry, delete the local row if nothing else is pending, and pull from scratch to restore the server's copy.
- **426** → keep the outbox, stop syncing, update at the next idle (§4.5).
- **Network / 5xx / 429 / 403** → keep the entry and retry with backoff and on reconnect. 403 is the Origin check (a screen opened at an address other than `APP_URL`), so the change waits instead of being dropped.

**Pull.** Every write bumps a global `sync_state.version` in the same transaction and copies it to the row. `GET /api/sync?since={cursor}` returns `{ cursor, changes: [{ entity, row }] }` for the account's tags, events, notes, photos and settings with `version > since`, tombstones included. The client applies them in one transaction, skipping rows with a pending outbox entry.

**Versions commit in order.** Every write runs in a `Database.tx`, and transactions run one at a time (D7: every `tx` takes the `sync_state` row lock first), so version *n* commits before *n + 1* is handed out by `stamp()`. A no-op write bumps nothing. `pullChanges` reads in one transaction too, so it never sees a write half done. So a cursor never skips a version.

**Conflicts** (SYNC-03)
- **Delete wins.** A `PUT` on a tombstone returns the tombstone unchanged.
- **Settings are one row.** The last write replaces the whole JSON.

**Triggers.** `GET /api/sync/stream` (SSE) sends `data: {"version":n}` when the account changes, with a `: heartbeat` every 25 s and nothing on connect. The bus is an in-process EventEmitter keyed by account. The stream has no build check (`EventSource` can't send headers); the pull that follows does.

## 6. Server design

### 6.1 Route handlers
`runtime = 'nodejs'`. Steps: Origin check (writes only) → build check (426; the sign-in routes `code`, `code/verify`, `verify`, `status`, `name`, `signout` and `signout-all`, `DELETE /api/account`, and `client-errors`, skip it) → session (`requireDisplay`, 401; `client-errors` doesn't need one) → Valibot parse (400) → service → map the `Result` to JSON. Errors are `{ error: code }` with 400/401/403/404/409/413/415/426/429/502/507. No middleware for auth. Helpers in `server/http.ts`; handlers import service indexes, never `server/db`. ### 6.2 Auth (SIGNIN-*)
1. `POST /api/auth/code { email, timeZone }` → 204. Email trimmed and lowercased; the email's older code is replaced (only the newest works); same answer whether the account exists. Limits: 5 per email and 20 per IP per 10 min (in memory) → 429. Failed send (`mail-failed`) → 502.
2. `POST /api/auth/code/verify { email, code }` → `signed-in { account, returning, setupDone }` with a new display and session cookie, creating the account if new (`time_zone` from the code row) and deleting the row. Otherwise 400 `wrong-code` (tries counted), `code-locked` (the 5th wrong try, or any try after it) or `code-expired` (≥ 10 min, or no live code: an unknown email reads the same). 30 per IP per 10 min → 429. Codes compare in constant time.
3. `GET /api/auth/verify?t=` (QR links only, D23) → 303 to `/signin?link=opened` with a session for the opening device, or `/signin?link=stale` (unknown, used, voided or past its expiry: 3 min, 10 for an import code). The link is read, checked and marked used in one transaction, so two scans at once sign in one device. A link made for Photos carries `&to=photos`, passed on only to an opened link (`/signin?link=opened&to=photos`); the sign-in screen reads it with `openedViewFrom`, says "Opening Photos…" and opens `/photos` instead of Today. An import link (`to=import`) also carries `&forDisplay=` = the link's issuing display (`verifyQrLink` answers it as `forDisplay`); `openedPath(search)` in `features/signin/signIn.ts` turns it into `/settings/import?forDisplay=…` ("Opening Import events…"). `POST /api/auth/verify { t }` (Scan to sign in, D33) runs the same check and answers `signed-in { account, returning, setupDone }` with the session cookie, or 400 `link-stale`; it skips the build check like the other sign-in routes. `GET /api/auth/status`: a valid session → `signed-in { account, returning, setupDone }`, else `signed-out` (a revoked token too; the device learns `revoked` from its next sync).
4. `POST /api/auth/name { name }` saves the name (≤ 100 chars) and, when the account has no tag yet, creates the first tag with that name and the first color in the same transaction. `POST /api/auth/location` saves the SIGNIN-14 place or a skip and sets `accounts.setup_done_at`.
5. `POST /api/auth/signout` deletes this display's session, display row and push subscription. `POST /api/auth/signout-all` revokes every session of the account and removes its screens (D31), clears the cookie and answers 204; this screen then signs out like a plain sign-out and opens `/signin?toast=signed-out-all`.
6. `POST /api/auth/qr` makes a one-time QR link for this display (voiding its older one; 30/hour); an optional body `{ opens: "photos" }` (`QrIssueRequestSchema`, `QR_OPENS` in `domain/qrSignIn.ts`; no body is the plain SIGNIN-15 code) adds `to=photos` to the link. `Transport.issueQr(opens?)` and `useQrTile(opens?)` pass it; Today's and Photos' "Add from your phone" codes use `"photos"` (PHOTO-03). `"import"` adds `to=import` and makes the link last 10 minutes (IMP-04); it opens `/settings/import?forDisplay=` (step 3), and `ImportScreen` reads that parameter once and sends it with every upload, so the file is staged for the issuing display (the link's `display_id`). Life comes from `qrTtlMs(opens)` in `domain/qrSignIn.ts` (`IMPORT_CODE_TTL_MS`, else `QR_CODE_TTL_MS`), used by the server's expiry and by `qrSecondsLeft(issuedAt, now, opens)`. `useQrTile` adds `renew()` (New code: a fresh code now, like 0:00). The waiting step (IMP-04) shows `useQrTile("import")` while it is open (closing it voids the code) and polls `ImportsRepo.staged()` every 3 s, skipping the import this screen staged itself. `DELETE /api/auth/qr { url }` voids it. A stale QR never reveals the account email.

`requireDisplay` resolves the session cookie to `{ displayId, accountId }` and stamps `last_seen_at`. Displays store `kind` and `browser` from the `User-Agent`.

**Mailer** (`server/mail/`). Auth takes a `Mailer` in its deps and never sees a provider.

```ts
type MailMessage = { to: string; subject: string; text: string; html?: string };
type Mailer = { send(message: MailMessage): Promise<Result<void, "mail-failed">> };
```

- **Sign-in email**: `signInMessage(to, code, season)` (`mailer.ts`) → `{ to, subject, text, html }`, with the HTML in `signInHtml.ts`: `emails/sign-in-code.html` as a template string (tables, inline styles, Arial and Courier New), every word from `copy.signIn.email`, the email HTML-escaped. `season` is the account's fixed season, else `seasonFor("auto", now, timeZone)` in the request's time zone; it picks the hero and page colors (Spring `#dceeb1`/`#f4ecd6`, Summer `#f6e3a1`/`#f4ecd6`, Fall `#f0c987`/`#f4ecd6`, Winter `#d5e4f1`/`#e9edf3`).
- **Contract** (`mailer.ts`): the sender is bound from `MAIL_FROM` when the mailer is built, so messages carry no `from`. Any failure (a non-2xx answer, a network or SMTP error) is `mail-failed`, never a throw. One attempt, no retry. A failure is logged once (`mailFailed`, `mail/send-failed`, §6.6) with the provider and the status or error, never the message or the provider's answer (they hold the sign-in code). `parseAddress` splits `MAIL_FROM` into `{ email, name? }` and is the env check for it.
- **Adapters**: `createResendMailer(config, from, fetch)` (`resend.ts`) → `POST https://api.resend.com/emails`, Bearer key, JSON `{ from, to, subject, text, html }`. `createMailtrapMailer` (`mailtrap.ts`) → `POST https://send.api.mailtrap.io/api/send`, or `https://sandbox.api.mailtrap.io/api/send/{inboxId}` when an inbox is set, Bearer token, JSON with `from: { email, name }` and `to: [{ email }]` (`parseAddress` splits `MAIL_FROM`). `createMailgunMailer` (`mailgun.ts`) → `POST https://api.mailgun.net/v3/{domain}/messages` (`api.eu.mailgun.net` for `eu`), Basic `api:{key}`, form-encoded fields. The three share one `postMail` step (`http.ts`). `createSmtpMailer(transport, from)` (`smtp.ts`) calls `transport.sendMail({ from, ...message })` on a minimal `SmtpTransport` type, so tests pass a fake; the factory passes `nodemailer.createTransport({ host, port, secure, auth })`. The `mailpit` provider reuses it with `secure: false` and no auth.
- **Factory** (`index.ts`): `createMailer(config, from, fetch = globalThis.fetch)` switches on `config.provider`. `mailer()` builds it once from `env().mail` and `env().MAIL_FROM` and is shared by auth.
- **Tests**: one contract suite (`contract.ts`: an accepted message → `ok`; a rejected message and an unreachable provider → `mail-failed` without throwing; logs never hold the message text) runs against the HTTP adapters on a fake `fetch` and the SMTP adapter on a fake transport. Each adapter's tests check the URL, auth header and body encoding, plus Mailtrap's sandbox URL and Mailgun's EU host. The factory is checked to reach each provider.

### 6.3 Photos
`POST /api/photos` takes one file per request as the raw body (XHR, so progress is real): `Content-Type`, `Content-Length`, URI-encoded `x-file-name`, optional `x-file-modified` (ISO date). The server runs `uploadProblem` on the declared type and size, reads the body into memory stopping at 20 MiB (`20 × 1024 × 1024` bytes; 413 `too-large`), decodes it and makes the two WebP copies with `sharp` in memory (415 `not-a-photo`), reads details (D22), checks the account's storage (D32; 507 `storage-full` before anything is stored), puts the two copies in parallel as `image/webp`, then inserts the row with its `bytes` and the next version and answers 201. A failed upload removes its objects and leaves no row. The upload queue is in memory on the client; it isn't kept across reloads.

`GET /api/photos/{id}/file?v=display|thumb` (session only, no build check since `<img>` can't send headers) streams the object through the server (so session auth and the SW photo cache stay same-origin) with its stored content type, `Cache-Control: private, max-age=31536000, immutable` and `nosniff`; 400 `invalid` for any other `v` (including `orig`), 404 for a tombstone or a missing object. `DELETE` removes the two objects and any old `.orig` after commit; a failed remove is retried by the daily job.

**Photo store** (`server/storage/`). Services and jobs take a `PhotoStore` in their deps and never see paths or buckets.

```ts
type StoredObject = { body: ReadableStream<Uint8Array>; size: number; contentType: string };
type PhotoStore = {
  put(key: string, body: Uint8Array, contentType: string): Promise<void>;
  get(key: string): Promise<Result<StoredObject, "not-found">>;
  remove(keys: string[]): Promise<void>;
};
```

- **Contract** (`store.ts`): keys are `{file_path}.{variant}`. `remove` of a missing key succeeds, and `remove` settles every key before it throws (both adapters use `allSettled`). Only `not-found` is a `Result`; disk and network failures throw (500).
- **Adapters**: `createDiskStore(root)` (`disk.ts`) writes under `{DATA_DIR}/photos`; on read the display and thumb copies are `image/webp` and any other key's type is sniffed. `createS3Store(config, fetch)` (`s3.ts`) signs single-request `PUT`, `GET` and `DELETE` calls with **`aws4fetch`** (SigV4) for AWS S3 and any S3-compatible endpoint; an S3 404 maps to `not-found`. AWS buckets are addressed virtual-hosted (`https://{bucket}.s3.{region}.amazonaws.com/{key}`); a custom `endpoint` (S3-compatible hosts, R2) is addressed by path (`{endpoint}/{bucket}/{key}`).
- **Factory** (`index.ts`): `createPhotoStore(config, fetch = globalThis.fetch)` switches on `config.kind`: `disk` → disk store at `{dataDir}/photos`, `s3` → S3 store, `r2` → S3 store with `endpoint = https://{accountId}.r2.cloudflarestorage.com` and `region = auto`. `photoStore()` builds it once from `env().storage` and is shared by services and jobs.
- **Tests**: one contract suite (`contract.ts`: put then get, missing key → `not-found`, idempotent `remove`) runs against the disk store on a temp dir and the S3 store on a fake `fetch` (`fakeS3.ts`, an in-memory bucket); the R2 config is checked to reach the R2 endpoint.

### 6.4 Jobs
`bootServer()` (from `instrumentation.ts`) prepares the database (`prepareDatabase()`: PostgreSQL migrates), exits on failure, then `startJobs()`: an hourly `unref` timer plus a tick at boot; daily jobs run on the first tick of each UTC day; a second `unref` timer runs the reminder job every minute. A failing job is logged with its name (`job/job-failed`, §6.6) and doesn't stop the others: `createJobTick({ hourly: { expireNotes, removeStagedImports }, daily: { cleanupSignIns, removeDeletedPhotoFiles, cleanupReminderSends } })` guards each one, and each job's name is its key there (the production server bundle is minified, so function names aren't kept). The start-up photo jobs (`removePhotoOriginals`, `backfillPhotoBytes`) and the minute's `sendReminderPushes` log failures the same way. Jobs run across accounts.
- **Note expiry** (hourly): tombstones notes older than the account's `noteExpiry.days` while it is on, using the screens' `noteExpired` rule, then publishes each account's version on the bus.
- **Code and link cleanup** (daily, `cleanupSignIns`): deletes `sign_in_codes` and `magic_links` expired more than 24 h ago, and `revoked_sessions` older than 400 days (the cookie's life).
- **Deleted photo files** (daily): removes the stored objects of tombstoned photos not yet marked `files_removed`, and marks each one removed, then the files listed in `photo_file_cleanup` (deleted accounts, D31), deleting each row once removed; one photo's failure doesn't stop the rest and is logged on its own (`job/cleanup-failed` with the `photoId`, §6.6).
- **Staged imports** (hourly, `removeStagedImports`): deletes `imports` rows still `staged` an hour after `created_at` (D39).
- **Reminder pushes** (every minute, D30): sends each due reminder once to the account's push subscriptions and prunes gone ones. Reminder sends older than a day are deleted by the daily cleanup.

`accountTimeZone(db, accountId)` = the saved place's `timeZone`, else the account's; the upload-day fallback reads it. Backups belong to the PostgreSQL host.

### 6.6 Error logging
Every error, on the server or on a screen, is **one JSON line on stderr**, written only by `logError(source, event, error, context?)` in `server/log.ts`; screens send theirs to the server (**Client errors** below). It is the only file in `src/server` and `src/app/api` that may use `console` (Biome `noConsole`, with an override for `log.ts`). No log service: the server runs under systemd, so the journal stores, stamps and rotates the lines.

**Where errors are logged.** Once, at the step that turns a thrown error or a bad answer into a `Result` error code (`getJson`, `mailFailed`, the push sender, the photo store calls); code that only passes the `Result` on never logs it again. Uncaught throws are logged by three catch points only: `onRequestError` in `instrumentation.ts` (every request error Next reports: Route Handlers, and server renders too), `runSafely` in `jobs/schedule.ts` (jobs, with the job's name from `createJobTick`, §6.4) and `bootServer` (start-up, then exit). The `pg.Pool` has an `error` listener (`db/pool-error`), so a dropped idle connection is logged instead of ending the process, and a failed `ROLLBACK` is logged (`db/rollback-failed`) while the original error is rethrown. `getJson` logs a throw (network, timeout, a body that isn't JSON) as `fetch-failed`, a non-2xx answer as `bad-status` with an `Error` `status {n}`, and a body that fails its schema as `bad-response` with `bad body at {paths}` (the failing dot paths, never the values, which can echo the coordinates); Open-Meteo's forecast that `toForecast` can't map (it answers the Valibot issues) and a time zone `isTimeZone` rejects (`unknown time zone {zone}`) are `bad-response` too. A photo's place lookup that throws is `weather/fetch-failed` without a `host`; one that answers `weather-failed` was already logged by `getJson`. A file `sharp` can't decode is `photos/decode-failed`; one it reads but that isn't a photo type is a quiet `not-a-photo`. A failed photo object remove is `storage/remove-failed` on delete or account deletion and `job/cleanup-failed` in the daily job, one line per photo. Next.js also prints its own plain-text line for an uncaught route error; the `jq` recipes below skip it.

**Line format.** Keys in this order:

| Key | | Value |
|---|---|---|
| `level` | always | `"error"` |
| `time` | always | ISO 8601 UTC with ms, `2026-10-26T14:03:11.482Z` |
| `source` | always | from the table below |
| `event` | always | kebab-case, from the table below; never renamed, so searches keep working |
| context | optional | only the keys below |
| `error` | always | `{ name, message, code?, stack?, cause? }`; `cause` has the same shape, at most 2 levels; a string becomes `{ name: "Error", message }` |

| `source` | `event` | Context |
|---|---|---|
| `route` | `request-failed` | `method`, `route`, `digest` |
| `job` | `job-failed`, `cleanup-failed` | `job`, `photoId` (cleanup) |
| `boot` | `start-failed` | — |
| `db` | `pool-error`, `rollback-failed` | — |
| `mail` | `send-failed` | `provider`, `status` |
| `weather` | `fetch-failed`, `bad-status`, `bad-response` | `host`, `status` |
| `push` | `send-failed` | `status` |
| `storage` | `remove-failed` | `accountId`, `photoId` |
| `photos` | `decode-failed` | `accountId` |
| `client` | `zone-crashed`, `page-crashed`, `uncaught`, `worker-crashed`, `outbox-watch-failed`, `sw-crashed` | `page`, `build`, `component`, `digest`, `occurredAt`, `timeZone`, `accountId`, `displayId`, `ip`, `browser`, `device`, `userAgent` |

A new failure kind adds its row here first. Context keys (the `logError` type allows no others): `method`; `route` (Next's `routePath`, `/api/events/[id]`, never the real path, whose query can hold a sign-in token); `job`; `provider`; `host` (never the full URL, which holds the family's coordinates); `status` (the upstream HTTP status); `accountId`, `photoId`, `displayId` (UUIDs); `page` (a screen's `location.pathname`, never its query); `build` (the screen's `CLIENT_BUILD`); `component` (the React component that crashed); `digest` (Next's id for a server render error: the server's `request-failed` line and the screen's `page-crashed` report carry the same one); `occurredAt` (when the screen caught the error, which differs from `time` for a report that waited offline) and `timeZone` (the screen's IANA zone), both from the report; `ip` (the client IP with the last IPv4 octet zeroed, or only the first three IPv6 groups, a /48), `browser` and `device` (`deviceOf`) and `userAgent` (cut to 300 characters), all read from the request, never from the body.

**Privacy.** `error` is copied field by field from the list above, so pg's `detail` (row values), a `WebPushError`'s `endpoint`, `headers` and `body`, and provider answers never reach the log. Email addresses in `message` and `stack` become `[email]` (SMTP errors name the recipient), and `message` is cut at 500 characters. Never logged: full IP addresses, emails, sign-in codes, session or QR tokens, push endpoints or keys, mail content, coordinates, event, note or photo text, request bodies, query strings.

**Client errors** (D37). Nothing on a screen logs to the console; it reports to the server, which logs the report as `source: "client"`.
- **Reporter** (`data/repos/clientErrors.ts`): a `ReportError` function `(event, error, extra?)` builds `{ event, error: { name, message, stack? }, page?, build, component?, digest?, occurredAt, timeZone }` (a thrown non-`Error` becomes `{ name: "Error", message: String(value) }`) and sends it with `fetch("/api/client-errors", { method: "POST", keepalive: true })`, so a report sent just before a reload still goes out. It cuts every string to the route's caps first, so a long stack is shortened rather than refused. `createErrorReporter({ fetch, events, online, page, now, timeZone })` makes one; per page load (and per worker) and per hour: one report per error (same `message` and first stack frame) and at most 20. Each new hour clears both, so a display that runs for weeks keeps reporting and a repeated error shows up once an hour. Offline, reports wait in memory and go on `online`; reports still waiting are lost on reload. It never throws, and a failed send is dropped without a report of its own. It is the only code that calls the route; every catch point (page, sync worker, service worker) makes its reporter with `createErrorReporter`, and `src/clientErrorGuard.test.ts` fails if any other source file names `/api/client-errors`.
- **Catch points** (only these): `ZoneBoundary.componentDidCatch` → `zone-crashed` with the first line of React's `componentStack` (the zone still shows its failed state, FAIL-01). `ui` can't import `data`, so `ui/crashReport.ts` holds a context with a no-op default, and `shell/ErrorReporter` provides `reportPageError` in it: the page's one reporter (made on first use, `page` = `location.pathname`), which `CrashScreen` calls directly, since `app/global-error.tsx` replaces the root layout and its context. `app/error.tsx` and `app/global-error.tsx` render `shell/CrashScreen` (FAIL-04), which reports `page-crashed` once on mount, with the error's `digest` when Next gave one; it sits outside `DisplayProviders`, so it runs its own `NowProvider` for the 60 s countdown. `shell/ErrorReporter`, wrapped around everything in the root layout, listens to `window` `error` and `unhandledrejection` → `uncaught`. `sync.worker.ts` listens to `self` `error` and `unhandledrejection` → `worker-crashed`, and `watchOutbox`'s `liveQuery` error → `outbox-watch-failed`; the worker gets the reporter through `WorkerDeps.report` (`liveWorkerDeps` makes one) and sends no `page`. `app/sw.ts` listens to its own `error` and `unhandledrejection` → `sw-crashed`, with a reporter from `data/sw/errors.ts` (no `page`). Expected failures (network, permissions, the service worker's cache steps) are `Result`s or quiet catches, not reports.
- **Route** `POST /api/client-errors` (§6.1): `Origin` check, no build check (old builds are the ones that crash) and no session needed, so `/signin` reports too. `ClientErrorSchema` (`domain/schemas.ts`) caps every string (`name` 100, `message` 500, `stack` 4,000, `page` and `component` 200, `digest` 100, `timeZone` 64 characters, `page` starting with `/`, `occurredAt` an ISO timestamp; both new fields optional, so older builds still report). `server/services/clientErrors.ts` `logClientError(sender, report, client)` takes `{ accountId, displayId }` from the session, else `{ ip }` (`clientIp`), and `client` `{ ip, userAgent }` from the request headers for every report, allows 30 reports per 10 min per display or IP (`createRateLimiter`), and calls `logError("client", report.event, report.error, …)`, which applies the same privacy rules. The answer is 204 whether logged or limited (400 for a bad body, 403 for a bad `Origin`), so the screen never retries. `accountId` and `displayId` come only from the session, never from the body.
- **Stacks**: `productionBrowserSourceMaps` is on (the source is public on GitHub), and `*.map` files stay out of the service worker precache (its `globPatterns` list no `.map`). To read a minified stack, check out the commit for the line's `build` and resolve it with `npx source-map-cli`.


**Reading the log** on the server (the unit is called `glance` here; use yours). systemd sends stdout and stderr to the journal; `-o cat` drops the journal's own prefix, and `jq -R 'fromjson?'` keeps only the JSON lines, so Next's plain-text lines and anything else are skipped. Pick the time with `--since` / `--until` (`"1 hour ago"`, `"2026-10-26 08:00"`, `today`) or `-b` for since the last boot.

```bash
# One readable line per error
journalctl -u glance -o cat --since today | jq -Rr 'fromjson? | select(.level == "error") | "\(.time)  \(.source)/\(.event)  \(.route // .job // .provider // .host // "-")  \(.error.message)"'

# Follow new errors live
journalctl -u glance -o cat -f | jq -Rr --unbuffered 'fromjson? | select(.level == "error") | "\(.time)  \(.source)/\(.event)  \(.error.message)"'

# Full entries, pretty-printed, for one source or event
journalctl -u glance -o cat --since "1 hour ago" | jq -R 'fromjson? | select(.level == "error" and .source == "weather")'

# A stack trace with real line breaks
journalctl -u glance -o cat --since today | jq -Rr 'fromjson? | select(.event == "request-failed") | .time, .route, .error.stack, ""'

# Count errors by source/event
journalctl -u glance -o cat --since "7 days ago" | jq -Rn '[inputs | fromjson? | select(.level == "error") | "\(.source)/\(.event)"] | group_by(.) | map({key: .[0], value: length}) | from_entries'

# One household's errors
journalctl -u glance -o cat --since today | jq -R --arg id "<accountId>" 'fromjson? | select(.level == "error" and .accountId == $id)'

# Screen errors only, with page, build and component
journalctl -u glance -o cat --since today | jq -Rr 'fromjson? | select(.source == "client") | "\(.time)  \(.event)  \(.page // "worker")  b\(.build)  \(.component // "-")  \(.error.message)"'
```

How long the journal keeps lines is set by `SystemMaxUse=` (size) or `MaxRetentionSec=` (age) in `/etc/systemd/journald.conf`.

**Tests**: `log.ts` has one suite: key order, the error fields copied and nothing else, `cause` depth, emails masked, the 500-character cut, a string error, a plain-object error. Server tests read the lines through `spyOnLoggedErrors()` (`server/testLog.ts`): `getJson` logs the host and status but never the coordinates, the push sender never logs the endpoint or keys, the photo cleanup job logs each failure, the pool listener logs, and a failed `ROLLBACK` is logged while the original error is rethrown. The reporter's tests cover one report per error, the cap of 20, both starting over each hour, the digest, `occurredAt` being the time of the error and not of the send, waiting while offline, never throwing and a non-`Error` value. `logClientError` has tests for the session's ids winning over the body, the masked IPv4, IPv4-mapped and IPv6 addresses, the browser, device and cut user agent, the IP limit for signed-out screens and the rate limit. A `Zone` test checks that a crashing child reports `zone-crashed` and still shows the failed state; `CrashScreen` has tests for reporting once, the digest, the countdown and Reload, `ErrorReporter` for the window's events, the worker for `outbox-watch-failed`, and the route for 204 (also for `sw-crashed` with a digest), 400 and 403.

### 6.8 Public events API (API-*)
Bearer key instead of the session: no Origin check (no cookies to ride on) and no build check. Steps: `apiAccount` (`server/http.ts`) → `requireApiKey(authorization)` (`server/auth/apiKeys.ts`): the header must be `Bearer glc_live_` + 32 base62, else 401; the key's SHA-256 is counted on the auth deps' `apiKey` limiter (60 per minute per key, in memory, `createRateLimiter`; over it → 429 `limited` with `Retry-After` = `ceil(retryAfterMs / 1000)` seconds, the key's window left); then `apiKeys.use(keyHash, now)` sets `last_used_at` and answers the account id in one `UPDATE … RETURNING` (no row → 401 `unauthorized`, so a revoked key fails at once). Body and query parse with `ApiEventInputSchema`, `ApiEventPatchSchema` (`v.partial`) and `ApiRangeSchema` (`domain/schemas.ts`); a body failure → 400 `{ error: "invalid", field }` with the first issue's top-level key.

`server/services/apiEvents.ts` maps between the API's event JSON (`ApiEvent`, API-03) and `CalendarEvent`, and saves through `events.putEvent` / `events.deleteEvent`, announced on the sync bus like any write, so screens, sync and reminders see it as a normal event:

| Function | Route | Notes |
|---|---|---|
| `listApiEvents(accountId, { from?, to? })` | `GET /api/v1/events` → `{ events }` | Live events of the account (`events.changedSince(accountId, 0)`), local day by `eventDayKey` in `accountTimeZone` (the location's zone, else `accounts.time_zone`, LOC-07); a series is kept while its first day ≤ `to`; sorted by `startAt` |
| `readApiEvent(accountId, id)` | `GET /api/v1/events/{id}` | 404 for a deleted id or another account's |
| `createApiEvent(accountId, input)` | `POST /api/v1/events` → 201 | New UUIDv7 id, `notify: true` |
| `changeApiEvent(accountId, id, patch)` | `PATCH /api/v1/events/{id}` | The stored event as API JSON, the patch spread over it (`null` clears an optional field), then built as a create; keeps `notify` and `importId` |
| `deleteApiEvent(accountId, id)` | `DELETE /api/v1/events/{id}` → 204 | 404 when already deleted |

Building checks what the schema can't, answering the field as the error (→ 400 `{ error: "invalid", field }`): `start` must be a `YYYY-MM-DD` date exactly when `allDay` (stored as UTC midnight, `allDayStart`); `end` must be after `start` on the same local day and absent for all-day (`end`); every `who` name must match a live tag of the account ignoring case (`who`); `who` absent → `everyone`, `[]` → no one, names → their tag ids in tag order (`created_at`). Timed `start`/`end` are stored and answered as UTC ISO strings.
